本文对应上一轮问题清单里排定的十项。每一项都写清三件事：**原来哪里有问题、怎么改的、

## 1. BTreeLatch 写路径扩展性

### 问题
`insert()` 先调 `update_existing()` 做一次完整下降，失败后再持 `writer_guard_`（tree-wide
mutex）从根重新下降一次。于是每个新 key 付两次下降，且所有写者在一把 mutex 上排队。
上一轮实测 insert 在 t32 只有 0.31 M ops/s，t32/t1 = 0.11。

### 改动
- 去掉 `writer_guard_`。`root_guard_` 只保护根指针，仅在**根创建 / 根分裂 / 根收缩**时排他。
- 写路径改为单次下降：共享锁下到叶子，叶上取排他锁；命中已存在 key 直接更新，叶子有余量
  直接插入；叶子满才转入 Bayer-Schkolnick 排他 crabbing（子节点 latch 到位后才释放父节点）。
- 容量判断移到**持有 root latch 之后**：原实现在探测和下降之间，别的线程可能已经把根填满，
  导致分裂无处安放而返回 WAIT，而那时分裂出的右半页已经挂到根上了（真实踩到的内存错误）。
- 叶分裂时先 latch 右兄弟再改它的 `prev`，避免相邻叶并发分裂撕裂兄弟链。
- `size_` 改为 `atomic`。

### 证据（`rrl_latch_path_bench`，order=128，3 次中位数）

| threads | insert 前 | insert 后 | 倍数 | update 前 | update 后 |
|---:|---:|---:|---:|---:|---:|
| 1 | 2 900 430 | 3 445 150 | 1.19× | 3 205 690 | 2 918 320 |
| 4 | 1 179 030 | 2 933 630 | 2.49× | 4 328 430 | 4 272 740 |
| 8 | 988 799 | 2 807 520 | 2.84× | 3 780 850 | 3 714 870 |
| 16 | 352 193 | 2 248 120 | 6.38× | 3 669 580 | 3 585 840 |
| 32 | 306 161 | 2 260 230 | 7.38× | 3 478 770 | 3 510 950 |

t32/t1 从 0.11 提到 0.66，即"新 key 插入不再被写路径串行化"。

真实负载上（只替换 B+树文件，其余代码完全一致）：ycsb-a t1 +3.6%、t8 −6.0%、t32 −4.1%；
ycsb-e t1 +1.3%、t8 −2.6%、t32 +0.3%。

### 遗留（重要）
隔离微基准里 update-only 在 t≥8 稳定慢约 20%，而同一个 update 路径的代码与旧实现逐行相同，
树高、size、op 数也完全一致。真实混合负载上只差 −4%~−6%，说明这是微基准特有的效应
（每线程独立 key 区间，父节点 latch 成为唯一共享点）。**这条没有解释清楚，按未结案处理。**

## 2. 远程事务缓存的全局互斥

### 问题
`txn_shards_mutex_` 一把锁同时保护"事务→分片"和"事务→已持锁"两张全局 map，每次 lock/unlock
都要过一次这把锁。

### 改动
拆成 64 个按 `txn_id % 64` 分片的缓存，每片独立 mutex，两张表同片。查询只碰一片。

### 证据
与第 4/6/7 项同批上线，没有单独 A/B。间接证据：单机回环 t=4 提交率从 5% 升到 78%（见第 6 项），
其中缓存不再全局串行是贡献之一。

## 3. 远程范围锁冲突扫描

### 问题
每个分片的 slot 表在冲突检查时被线性扫描，范围锁还要逐个解码、做区间重叠判断。
分片上限 1024 槽，一次请求最多扫 16 片。

### 改动
新增 `include/lock/slot_index.h`：把有下界的 slot 按 `start_key` 排序，并维护 end 的**前缀最大值**。
查询 `[qs, qe]` 时：
- `hi = upper_bound(starts, qe)`：所有 start ≤ qe 的区间；
- `lo = lower_bound(max_end, qs)`：第一个"前缀最大值 ≥ qs"的位置，它之前的所有区间都结束于 qs 之前，
  不可能重叠。

候选集从"整表"缩到 `[lo, hi)`，复杂度 O(log n + 命中数)。点锁走同一窗口，无界区间单独成表。
`find_owned` 复用同一索引，不再整表找自己已发布的槽。

### 证据
新增 `test/slot_index_test.cpp`：200 轮 × 200 次查询，随机生成 slot 与查询区间，
索引结果与暴力全表扫描**逐条对拍**，同时校验 `find_owned` 与线性查找一致。CTest 通过。

## 4. 远程解锁批量化

### 问题
`unlock` / `unlock_all` 逐分片处理，每片都要"抢 gate → 读计数 → 读槽 → 写槽 → 写计数 → 放 gate"，
16 片就是几十次往返，而且中途失败会留下半删状态。

### 改动
两者合并为一个 `release()`：一次批量抢 gate（`compare_swap_batch`）、一次批量读计数、一次批量读槽、
一次批量写（每个搬移的槽 + 每片的计数，超过 128 条自动分块）、一次批量放 gate。
QP 发送队列从 64 扩到 256。

**关键正确性改动**：释放路径改为**可靠等待**。原实现抢不到 gate 就 `return AbortGate`，
而它此时一把锁都没删——锁永久残留，后续事务撞上就被记成"冲突"。这正是上一轮跨主机
"每线程只能提交一个事务"的直接原因。

### 证据
单机回环、ycsb-e range=8、2000 事务：

| threads | 改造前 commit | 改造后 commit | 协议级 gate 中止（前→后） |
|---:|---:|---:|---:|
| 1 | 2000 | 2000 | 0 → 0 |
| 4 | 103 | 1584 | 1838 → 0 |
| 8 | 22 | 1515 | 1947 → 9 |
| 16 | ≈0 | 1425 | — → 0 |

跨主机（`.66→.67`，1000 事务）：t=1 两个协议均 1000/1000 提交；t=8 提交 730/1000（27% 中止），
而改造前是 87.5%（恰好 `1−1/8`，即每线程只提交一个事务）。

## 5. RDMA 超时与完成错误定位

### 问题
只有总超时数与总完成错误数。上一轮的"1 秒卡顿"只能靠 `transactions / attempt_tput` 反推。

### 改动
- `RdmaFailureInfo`：opcode、WC 状态、远程地址、长度、WR 序号、耗时、QP 号、阶段标签。
- 阶段标签 `RdmaOpTag`：Gate / LoadCounts / LoadSlots / StoreSlot / ReleaseGate，
  由锁管理器在发起请求前设置。
- `RemoteLockManager` 把失败地址换算回分片（`last_failure_shard()`）。
- runner CSV 追加 9 列：gate 尝试/重试/中止、批次数、失败 opcode/分片/WR 序号/耗时/QP。

### 证据
单机回环 2000 事务的运行里可直接读到 `rdma_gate_attempts=145414`、`rdma_gate_retries=76919`、
`rdma_batches=151136`，不再需要从吞吐反推。跨主机冒烟 6 个 case 的 `rdma_timeouts` 与
`rdma_completion_errors` 全为 0。

## 6. RDMA gate 竞争策略

### 问题
抢不到 gate 立刻 `AbortGate`。一次 gate 典型持有时间是若干次 RDMA 往返（微秒级），
而重试只是一次 CAS，所以绝大多数"冲突"其实是假冲突：请求晚到几微秒而已。

### 改动
`enter_shards` 分两档：
- **lock()：有界重试**，默认 64 次。前 4 次自旋，之后 1→64 µs 递增睡眠。有界是必须的：
  多分片获取是 all-or-nothing，无界等待会引入死锁风险。
- **release()：可靠等待**，指数退避最高 128 µs、上限 4096 次（最坏约 0.4 s）。理由见第 4 项。

`Diagnostics` 暴露 `gate_attempts / gate_retries / gate_aborts`，三者可直接判断"假冲突还剩多少"。

### 证据
单机回环、2000 事务、ycsb-e range=8：

| threads | 仅 no-wait | 有界重试 |
|---:|---:|---:|
| 4 | 103 | 1584 |
| 8 | 22 | 1515 |
| 16 | ≈0 | 996 |

t=16 仍有 539 次 gate 中止（重试耗尽），说明单分片 gate 的串行化在高并发下确实成为上限——
这是 gate 设计本身的成本，不是实现缺陷，已记入遗留。

## 7. 多 QP 与本地 gate 互斥

### 问题
每个分片有一把本地 `std::mutex`，把同进程内所有线程串行化。需要确认它是否抵消了 per-thread QP 的收益。

### 改动
先做出开关（`RRL_LOCAL_GATE`），做 A/B 之后再定默认值。**结论与预期相反**：本地互斥是有益的，
因为远程 CAS gate 本来就是串行点，本地 mutex 只是把"失败的 CAS 往返 + 重试"换成"进程内等待"。
因此默认改为**开启**。

### 证据（单机回环，2000 事务，ycsb-e range=8）

| threads | 本地 gate 关 | 本地 gate 开 |
|---:|---:|---:|
| 4 | 1584 commit / 0 gate abort | 1572 / 0 |
| 8 | 1483 / 8 | 1509 / 0 |
| 16 | 1003 / 552 | **1425 / 0** |
| 32 | 263 / 1472 | **1391 / 0** |

t=32 提交数 5.3 倍差距。吞吐在 t=8 略降（723→641），但完成的工作量更多。

### 遗留
"不同连接数的扩展曲线"没有做：`set_connection_count(threads)` 恒等于线程数，没有暴露
"固定 1 个 QP / 4 个 QP / 每线程 1 个 QP"的对比入口。需要再加一个 CLI 参数才能测。

## 8. v6 bucket 宽度策略

详见 `docs/notes/v6-bucket-width-2026-11-01.md`。结论：**没有单一默认值能同时适配两类负载**，
相同实现在 ycsb-e 上最优 256、在 ycsb-a 上最优 16，t=32 时相差 4 倍。已实现 `--bucket auto`
按负载选择（16 / 256 / 64），并在 CSV 末尾输出实际生效的宽度。

## 9. BTree erase 路径

### 问题
原来"删除不合并"的实现有真实缺陷：叶子删空后仍挂在树上，`first_key` 对空页返回 0，
分隔键与子树最小值脱节；`validate()` 也没有检查这一条，所以问题一直静默。

### 改动
- 叶子删空 → 从父节点摘除并修正分隔键，同时修兄弟链。
- 父节点若因此退化为"0 键 0 孩子" → 继续向上摘除，级联到根。
- 根失去全部孩子 → 收缩为空树；根只剩一个孩子 → 提升（树高下降）。
- **不做内部节点提升**：把一个 0 键 1 孩子的内部节点替换成它的孩子，会让该子树比兄弟浅一层，
  直接把树变成不平衡。这类"直通节点"保留在树上，留给未来的合并流程回收。
- `validate()` 增加三条不变式：所有叶子同深度、非根页非空、0 键内部节点必须恰好 1 个孩子。

### 证据
新增 `test/v2_btree_erase_test.cpp`：4096 key 预填 → 删不存在的 key（应 Abort 且不改树）→
隔一删一 → 随机排空（每 64 次校验一次结构，并断言高度不增长）→ 排空后重建 → 重复更新不产生重复 key。
另有一次性调试脚本对**每一次删除**都跑 `validate()`，从 4096 删到 0 全程通过。
ASAN 与 TSan 下均无报告。

## 10. 统计与 workload 驱动开销

### 问题
五个驱动每个操作做一次 `std::atomic` 自增，所有线程争用同一条缓存行——而这条路径正是被测量的对象。

### 改动
每线程一个 `alignas(64)` 的累加结构（填充到 64 的整数倍），结束时一次性归并。五个驱动共用 `merge_parts`。

### 证据（同一台机器、同一负载，与 `912887a` 对比，3 次中位数）

| 场景 | t | 改前 | 改后 |
|---|---:|---:|---:|
| zipf=0.5, keys=10k | 16 | 295 228 | 357 516 |
| zipf=0.5, keys=10k | 32 | 291 477 | 334 666 |
| zipf=0.5, keys=200k | 16 | 240 992 | 311 155 |
| zipf=0.5, keys=200k | 32 | 275 901 | 306 416 |
| **zipf=0.99, keys=10k** | **32** | **221 026** | **133 177** |

前四行是 +11%~+29%。最后一行**变慢 40%**，原因不是统计变慢，而是原子计数此前充当了隐式背压：
它把所有线程串在同一缓存行上，客观上降低了同时冲击叶子 latch 的线程数。去掉背压后，
`BTreeLatch` 的页锁争用直接暴露出来。这条结果本身是"索引层仍是瓶颈"的证据，已记入遗留。
