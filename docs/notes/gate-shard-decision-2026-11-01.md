# gate 是否继续优化：决策与后续方案（2026-11-01）

## 一、决策

**本轮不继续优化 gate，保留 16 分片 / 每片 1024 槽的现有实现，把它作为"协议基线"。**

不做 per-slot CAS，也不做 16/64/256 分片实验。理由分三层，最后一层是决定性的。

## 二、现有 gate 的实测位置

数据来自本轮及上一轮（同一台机器，单机回环）：

| 观测 | 数值 | 含义 |
|---|---|---|
| 单分片加锁服务率（t=16） | 约 26k 次/秒 | 每次 gate 独占约 38 µs |
| 一次 gate 的往返数 | 3–4 个 RDMA 往返 | CAS 抢门 → 读数 → 写槽 → 释放 |
| t=8–32 的 committed | 2 100–2 650，几乎不随连接数变化 | 串行点在 gate，不在 QP |
| 本地 gate 互斥 A/B（t=32） | 263 → 1 391 提交（5.3×） | 失败的 CAS 往返比进程内等待贵得多 |

也就是说：**gate 是跨主机路径的吞吐上限**，这一点已经确认，不需要再证明。

## 三、为什么本轮不动它

### 1. 研究对象是协议，不是传输层

项目的核心命题是 v3→v6 六种并发控制机制在**同一份 workload、同一份页布局**下的差异。
RDMA 通道的作用是"把锁表挪到远端，语义不变"。gate 的争用是所有版本共有的常数，
它压低了绝对值，但不改变版本之间的相对关系——本轮本地矩阵里五个协议的排序就是这么
读出来的。在这种情况下继续压 gate，得到的是传输层优化，不是协议结论。

### 2. 三个候选方案都要改线格式，改动量不对等

| 方案 | 改动 | 代价 |
|---|---|---|
| 增加分片数（16→64/256） | `RemoteLockShard::slots[1024]` 是线格式里的定长数组，`shard_base()` 用编译期偏移；改成运行期需要 region 头加 shard_count 字段、所有偏移改为算出来、服务端与客户端必须协商一致 | 中：改线格式，需要双向兼容检查 |
| per-slot CAS | 锁槽本身用原子操作抢占，不再需要 gate | 大：换数据结构，冲突判定从"读整表"变成"逐槽抢占 + 回滚"，next-key 的区间语义要重新论证 |
| 本地 gate 已做 | 进程内互斥 | 已完成，默认开启 |

方案 1 的收益也不是单调的：分片越多，一次多分片获取要抢的门越多。next-key 在 range=128
时跨 2–3 片，分片数 16→256 后同样的区间会跨 32–48 片，全或无的获取失败率反而上升。
**这一点必须先被设计论证，而不是先跑实验。**

### 3. 已有方案文档，但缺一个前提

`docs/notes/rdma-sharded-gate-plan.md` 描述的是"按逻辑 bucket 分片 + 区间副本"的完整设计，
它的前提是**区间到分片的映射可配置**。当前 `shard_ids()` 已经做了两件事：

- 有界区间按 `bucket_width_` 映射到覆盖的 shard；
- 无界区间的根意向锁（`LockKind::Node` + IS/IX）固定映射到 shard 0，避免全分片抢门。

第二点是 12b5890 引入的，它让"增加分片数"不再直接伤害 v6 的根锁。但区间副本、
跨分片去重、断开清理这几条还没有实现，所以现在跑 16/64/256 只会得到"分片数变了、
其余没变"的孤立数据，解释不了任何东西。

## 四、如果以后要做，先做这些

### 4.1 设计（进代码前必须先写清）

1. region 头加 `shard_count`，`shard_base(i)` 改成 `shards_address_ + i * shard_bytes`，
   `shard_bytes` 由 `slots_per_shard` 算出；服务端启动参数决定，客户端从握手读取，
   双方不一致时拒绝连接而不是各自算。
2. 多分片获取保持**升序抢门、逆序释放**（现有实现已是如此），并在获取失败时释放已拿到的门
   （本轮已修，`try_enter_shards` 的 TransportError 分支）。
3. 分片数变大后，next-key 的长区间会跨更多分片，需要先估计 `E[失败率]` 与
   `E[每次获取的门数]` 的关系，再决定是否需要"区间副本 + 单门代理"的混合策略。

### 4.2 定向实验（只跑三档，不跑完整矩阵）

| 维度 | 取值 |
|---|---|
| shard_count | 16 / 64 / 256（slots_per_shard 固定 1024，region 相应变大） |
| cc | `rdma-next-key`、`rdma-hierarchical` |
| workload | `ycsb-e`（range=8, 128）、`ycsb-a` |
| threads | 1 / 8 / 32 |
| 每次 | ≥10 秒窗口、3 次重复 |
| 必看指标 | `rdma_gate_attempts`、`rdma_gate_retries`、`rdma_gate_aborts`、`lock_capacity_aborts`、committed txn/s、`rdma_operations` |

判定标准（写在这里，避免事后解释）：分片数增加后，如果 `gate_retries/attempts` 没有下降
而 `rdma_operations`（每次请求的往返数）上升，就说明"抢门次数被区间跨度吃掉了"，
应当停在 16 或 64，不再往上加。

## 五、结论一句话

gate 是已确认的瓶颈，但它是传输层常数、不是协议差异；改它要动线格式或数据结构，
代价与本研究的问题不匹配。**本轮把它当基线固定下来，把扩展方案写清、把判定标准写死，
等协议对比结论定稿后再决定要不要动。**
