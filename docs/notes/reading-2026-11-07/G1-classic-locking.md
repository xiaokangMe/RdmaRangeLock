### 01 A Critique of ANSI SQL Isolation Levels（1995, ACM SIGMOD'95, San Jose）

- 一句话问题：ANSI SQL-92 用 Dirty Read / Non-repeatable Read / Phantom 三个 phenomenon 定义隔离级别，措辞含糊且漏掉 Dirty Write，导致「按现象定义的级别」与商用系统实际用的「锁调度器级别」不等价；需给出严格化定义并刻画 Snapshot Isolation。
- 锁对象 / 粒度：两类可锁对象——`data item`（行 / 页 / 表 / 队列消息）与 `predicate`（`<search condition>` 定义的、可能是无限的集合，含当前不存在但会被 INSERT/UPDATE/DELETE 变成满足条件的 phantom 数据项）。原文明确「An item lock (record lock) is a predicate lock where the predicate names the specific record.」（PAGE 3）。
- 冲突判定：同一 item 上两锁若至少一个是 Write 则冲突；两个谓词锁「conflict if one is a Write lock and if there is a (possibly phantom) data item covered by both locks」（PAGE 3）。即「一写 + 交集非空（含 phantom）」。历史层面用依赖图等价序列化 history 判定。
- 关键机制：把 P1/P2/P3 分为 strict（A1/A2/A3，要求真的发生 abort / 二次读 / 二次谓词求值）与 loose（P1/P2/P3，只要出现可能致异常的序列即禁止），论证 loose 才是 ANSI 本意；补出 P0（Dirty Write）；给出 Table 2「Degrees of Consistency and Locking Isolation Levels」——Degree 3 = Locking SERIALIZABLE = `Long duration Read locks (both items and predicates)` + `Long duration Write locks`；Degree 2 = 短谓词读锁 + 长 item 读锁；Cursor Stability = 当前游标项锁；论证「Prohibiting P3 means long-term Read predicate locks」（PAGE 6）。另定义 Snapshot Isolation（Start/Commit-Timestamp、First-committer-wins）、A5A Read Skew / A5B Write Skew。
- 正确性：只要所有事务 well-formed + 2PL，任何 legal schedule 都 serializable（PAGE 3「The fundamental serialization theorem is that well-formed two-phase locking guarantees serializability」）。防幻读要求「long duration Read locks on predicates」，即把谓词读锁持有到 EOT；REPEATABLE READ 只锁 item 不锁谓词，故 A3/P3 仍可能出现。SI 在严格 A3 意义上「has no phantoms」，但不排除 P3（PAGE 8 Remark 10、PAGE 8「However, Snapshot Isolation does not preclude P3」），这是本项目把 MVCC/SSI 排除出实现类别、但保留 P3 判据的直接依据。
- 代价：本文是定义/定理层，不给锁表实测；但给出可复现的自变量——锁的 `scope（item/predicate）× mode（R/W）× duration（short/long）`，以及「locking scheduler does not admit all possible Serializable histories」（PAGE 4）这一并发上界。谓词读锁覆盖的是无限集合，实现上必须退化为可枚举资源（见 13/16/36）。
- 与 RdmaRangeLock 的关系：对应综述「隔离级别与正确性口径」章节，定义 `detect_conflict(other)` 必须达到的语义下界（P3 被禁止 = 防幻读）。v3 record-2PL 只做到 REPEATABLE READ（不防幻读）；v4/v5/v6、predicate、exact-range 才达到 Degree 3。已实现：`predicate`/`exact-range` 是「长谓词读锁」的可枚举近似；可补：把 `mode` 与 `duration` 显式做成参数，验证 short/long 谓词读锁下 P3 是否出现。SI 按用户口径不建实现版本。
- 可复现性：可在现有 `lock(mode, key_range)` 接口下做成单变量版本：固定 `key_range` 为整段查询区间，唯一自变量是「读锁是否持有到 commit」（`unlock_all()` 只在 commit/abort 调用即为 long）。需新增：把 `<search condition>` 归一为 `[lo, hi)` 区间的能力（本项目已由 `exact-range` 具备），以及 P0/P1/P2/P3 四种 history 模式的 workload 生成器。不需要新增锁模式。
- 关键原文证据：
  - PAGE 3：「A Read (resp. Write) predicate lock on a set of data items determined by a given `<search condition>` is effectively a lock on all data items satisfying the `<search condition>`. This may be an infinite set, as it includes data present in the database and also all phantom data items not currently in the database but that would satisfy the predicate if they were inserted or if current data items were updated to satisfy the `<search condition>`.」
  - PAGE 3：「Two predicate locks by different transactions conflict if one is a Write lock and if there is a (possibly phantom) data item covered by both locks.」
  - PAGE 6：「Prohibiting P3 means long-term Read predicate locks.」/「Remark 6. The locking isolation levels of Table 2 and the phenomenological definitions of Table 3 are equivalent.」
  - PAGE 8：「Remark 10. Snapshot Isolation histories preclude anomalies A1, A2 and A3. Therefore, in the anomaly interpretation of ANOMALY SERIALIZABLE of Table 1: ANOMALY SERIALIZABLE << SNAPSHOT ISOLATION.」
  - 注：01 的 OCR 质量差（大量错字、断词），同一段落建议以 41 为准。

### 02 A Survey of B-Tree Locking Techniques（2010, ACM TODS 35(3), Article 16）

- 一句话问题：B-tree 并发控制的术语（row-level / key value / key range / lock coupling / latching / latch coupling / crabbing）混乱，需把主题拆成两个正交子问题并各给出统一框架。
- 锁对象 / 粒度：内容保护用 `lock`，可加在 page、B-tree key、或「gaps (open intervals) between keys」上；后两者分别叫 key value locking 与 key range locking。结构保护用 `latch`，加在 buffer pool 中的页/内存数据结构上。
- 冲突判定：基础 S/X 兼容表（Figure 1，PAGE 5）；key range locking 用层次锁兼容表 Figure 7（IS/IX/S/X，PAGE 18）；组合模式表 Figure 8 的兼容由两个分量分别兼容后取合取（PAGE 19：「XS is compatible with NS because X is compatible with N and S is compatible with S」）；increment/E 锁另有兼容表 Figure 10/11（PAGE 21–23）。
- 关键机制：① 二分框架——「distinguish protection of the B-tree structure from protection of the B-tree contents, and to distinguish separation of threads against one another from separation of user transactions against one another」（PAGE 2）；② key range locking 定义为半开区间，`next-key locking` 与 `prior-key locking` 只是「为保护相邻键之间 gap 而锁哪个键」的方向差异，next-key 需能锁人工键 `+∞`，prior-key 借最低值 `NULL`（PAGE 14）；③ `instant locks` = 「test without set」，验证能拿到 `+∞` 锁但不真正持有，「violate two-phase locking but work correctly if a single acquisition of the page latch protects both verification of the lock and creation of the new key on the page」（PAGE 15）；④ ghost/pseudodeleted 记录：删除只置 ghost bit，ghost 键仍参与 key range locking，删除只需锁 key 不需邻 gap；fence keys（页内最高/最低可能键，最高恒为 ghost）保证「key range locking never requires navigation to neighbor nodes」（PAGE 16）；ghost 增减会分裂/合并区间，锁集必须同步分裂/合并（PAGE 16–17）；⑤ 层次化 key range locking：大粒度=半开区间，小粒度=key value 或 open interval，用组合模式 `SN`（锁键 S、放开区间）、`NS`（不锁键、锁开区间，用于 phantom protection）、`XS` 等把「两次 lock manager 调用」压成一次（PAGE 18–19）；⑥ B-link tree 的 high fence key + 右邻指针把 split 拆成两步（PAGE 11–12）；latch coupling / crabbing（PAGE 10–11）。
- 正确性：「serializability requires locking not only the presence but also the absence of data」（PAGE 13）；只锁 key value 不锁 gap 就不能保证缺席（PAGE 15 Figure 4 第三、四种 scope）；key range locking「prevents phantoms for true serializability」（PAGE 23）。前提：读锁持到 EOT、写锁恒持到 EOT、latch 与 lock 严格分离、锁请求入锁表前必须持有页 latch 以保证被锁的键值仍存在，等待锁时释放 latch 并「repeat its root-to-leaf search for the key」（PAGE 15）。
- 代价：lock「often thousands of CPU cycles」且需锁表 hash + 链表、参与死锁检测（PAGE 6）；latch「tens of instructions only」、不参与死锁检测、可嵌入被保护数据结构（PAGE 6、PAGE 9）。层次化的代价权衡明确写在 PAGE 18：「locking a key (or an open interval) requires two invocations of the lock manager」，而组合模式可以在不增加调用数的前提下增加并发（PAGE 19、PAGE 23）。ghost 记录减少日志量与回滚时空间分配失败。
- 与 RdmaRangeLock 的关系：这是综述的「主轴参考」，直接支撑 v2（latch coupling）、v4/v5（gap / next-key / prior-key 同类）、v6（层次锁）、以及 `instant`/`exact-range` 的解释。已实现：v2/v4/v5/v6/predicate/exact-range；可补：`prior-key` 方向开关、`+∞`/`NULL` 哨兵开关、ghost/fence 开关、组合模式（SN/NS/XS）版本。
- 可复现性：最适合做「单变量版本」的一篇——它把 next-key/prior-key、instant、ghost、组合模式都表述为同一框架下的开关。在现有 `lock(mode, key_range)` 下，next-key 与 prior-key 只是 `key_range` 端点取 `(prev, k]` 还是 `[k, next)` 的差别，无需新增锁模式。需新增：① 索引能给出前驱/后继键与 `+∞`/`NULL` 哨兵；② `mode` 支持组合（range 分量 + key 分量）与 `instant`（test-without-set）语义；③ ghost bit 与 fence key 的 B+树叶结构能力。
- 关键原文证据：
  - PAGE 5：「Locks separate transactions using read and write locks on pages, on B-tree keys, or even on gaps (open intervals) between keys. The latter two methods are called key value locking and key range locking. Key range locking is a form of predicate locking that uses actual key values in the B-tree and the B-tree's sort order to define predicates.」
  - PAGE 14：「The usual form are half-open intervals including the gap between two neighboring keys and one of the end points, with "next-key locking" perhaps more common than "prior-key locking." The names describe the key to be locked in order to protect the gap between two neighboring keys. Next-key locking requires the ability to lock an artificial key value "+∞". Prior-key locking gets by with locking the NULL value, assuming this is the lowest possible value in the B-tree's sort order.」
  - PAGE 15：「Such "instant locks" violate two-phase locking but work correctly if a single acquisition of the page latch protects both verification of the lock and creation of the new key on the page.」
  - PAGE 3：「Mohan's ARIES/KVL design explicitly separates locks and latches... A key value lock covers both a gap between two B-tree keys and the upper boundary key.」「a single lock in ARIES/IM covers all index entries for a logical row even in the presence of multiple indexes.」
  - PAGE 3：「Lomet's design for key range locking [Lomet 1993] attempts to adapt hierarchical and multigranularity locking to keys and half-open intervals but requires additional lock modes, such as a "range insert" mode... Graefe's design [2007] applies traditional hierarchical locking more rigorously to keys and gaps (open intervals) between keys, employs ghost (pseudodeleted) records...」
  - PAGE 23：「key range locking is the technique of choice for concurrency control among transactions... prevents phantoms for true serializability.」

### 03 ARIES/KVL: A Key-Value Locking Method（1990, 16th VLDB, Brisbane, pp.392–405）

- 一句话问题：System R 的 key-value locking 虽能支持 RR，但 next-key 锁引发的 adjacent key conflict、页锁持到 RSS 调用结束导致的死锁、回滚事务死锁，使并发不足；需在只使用 System R 已有锁模式的前提下改进。
- 锁对象 / 粒度：`key value`（哈希成定长锁名，拼接 index ID 保证跨索引唯一，PAGE 4）；每个键值锁隐含覆盖「从前驱键到该键」的整个区间。另有 `EOF` 特殊锁名处理右边界、`tree latch` 与 `page latch` 处理结构。
- 冲突判定：S/X/IS/IX/SIX 兼容矩阵 Figure 2（PAGE 3）；核心是「IX 与 S 不兼容、IX 与 IX 兼容」，因此非唯一索引下同键值的并发 insert/delete 可用 IX 而非 X，而读者仍被排除。
- 关键机制：①「range locking via next key locking」——Fetch（含 not found）在「满足条件的键或下一个更高的键」上留 commit-duration S 锁，插入者必须先检查 next key 的锁（PAGE 5–6）；② `instant duration lock` 定义：「the lock is not to be actually granted, but the lock manager has to delay returning the lock call with the success status until the lock becomes grantable」（PAGE 3），insert 的 next-key IX 锁是 instant，delete 的 next-key X 锁必须 commit-duration（PAGE 6，原因：未提交插入可见、未提交删除不可见）；③ `lock state replication via next key locking`：若本事务已持有 next key 的 S/X/SIX，则新插入键改锁 X 而非 IX（Figure 1、PAGE 10–11 三个场景、PAGE 13）；④ `revalidation after unconditional locking`：conditional 请求失败则释放 latch、unconditional 请求、拿到后按页 `VN`（version number）重新校验并可能改锁别的键（PAGE 5、PAGE 8）；⑤ EOF 哨兵（PAGE 7）；⑥ 9 条设计原则（PAGE 13）：latch 管物理、锁等待时释放 latch、无条件加锁后重校验、VN、range locking via next key、lock state replication、SMO 由 tree latch 串行化、SM-Bit 标记未完成 SMO、latch-coupling；「At most 2 page latches are held simultaneously」；⑦ latch coupling 定义（PAGE 6）；⑧ 明确拒绝 predicate locking 的工程理由（PAGE 6）。
- 正确性：保证 RR/serializability（well-formed 2PL + 未在索引上显式违反），关键不变式是「未提交插入的键本身是 tripping point，未提交删除必须在仍存在且稳定的键上留下强锁让他人 trip on」（PAGE 12–13「an uncommitted insert is "visible"... whereas an uncommitted delete is not visible since the deleted key disappears from the index」）。前提：唯一索引用 X、非唯一可用 IX；所有 `> F` / 前缀 Fetch 延迟到叶页定位后再加锁；SMO 由 tree latch 串行。
- 代价：锁数——每个 Fetch 至少 1 把键值 S 锁，insert 至少 1 把 next-key instant + 1 把 current-key commit 锁，delete 至少 1 把 next-key commit + 1 把 current 锁；System R 的 next-key S/X 锁造成「adjacent key conflict problem」与并发下降（PAGE 13）。锁表为哈希表 + 链；instant 锁「does not consume any storage and it does not cause a hash synonym chain in the lock table to become longer」（PAGE 12）。latch 比 lock 便宜一个数量级（PAGE 2「10s of instructions versus 100s of instructions」）。明确给出拒绝谓词锁的代价理由：「checking for compatibility among predicates is much more expensive than checking for compatibility among locks. With the latter, the data structure is usually a hash table that can be looked up very efficiently. No such simple data structure exists for organizing a collection of predicates and comparing them.」（PAGE 6）。
- 与 RdmaRangeLock 的关系：v5 next-key 的直接原型，也是 v2 latch coupling 的出处；`instant` 与 `EOF` 哨兵是本项目 `no-wait / wait-die / wound-wait` 之外的「持续时间」维度的补充。已实现：v5 主干；可补：IX/SIX 用于键值锁、「lock state replication」、唯一/非唯一索引分支、EOF 哨兵的显式实现。
- 可复现性：`lock(mode, key_range)` 已能表达（把 `key_range` 取 `(prev, k]`，`mode` 取 S/X/IX/SIX）。要完整复现需新增：① `instant` 持续时间（`lock()` 只检查冲突不入锁表）；② `EOF`/`+∞` 特殊键值；③ 索引的 next-key 查询与页 VN 版本校验；④ 组合 `detect_conflict` 时区分「本事务已持有 next key 的何种模式」以决定是否升级为 X。单变量自变量：next-key 锁持续时间（instant vs commit）、mode（X vs IX）。
- 关键原文证据：
  - PAGE 5：「Thus, a lock on a key value is really a range lock on the range of keys spanning the values from the preceding key value that is currently present in the index to the locked key value. For this range-locking protocol to work, the inserting transaction must check the lock on the next key value, before it does the insert of a given key value.」
  - PAGE 6：「We call this design principle range locking via next key locking. This is a conservative approach since the nongrantability of the X lock on the next key is interpreted to 'imply that the holder of that lock does not want the insert to happen until the holder terminates, when in fact the holder might have the lock on the next key for a totally different reason'.」「Hence, the next key lock is requested for instant duration during an insert operation.」
  - PAGE 7：「If Fetch reaches the last (i.e., the rightmost) leaf page and no matching or higher key value is found, then it is treated as the EOF (End Of File) situation and a special lock name unique to this index is used as the found key value's lock name.」
  - PAGE 10：「This we call lock state replication via next key locking. We are essentially transferring a range lock from the next key to the current key.」
  - PAGE 13：「(5) range locking via next key locking, (6) lock state replication via next key locking...」「ARIES/KVL brings us closer to the power of predicate locking using only traditional locking and without using any additional lock modes other than the ones introduced in System R.」
  - PAGE 13：「As far as we know, System R was the first system to do key-value locking and support RR.」「This has been termed the adjacent key conflict problem and customers have suffered reduced concurrency due to this also.」

### 04 ARIES/IM: Efficient and High Concurrency Index Management Using WAL（1992, ACM SIGMOD'92, San Jose, pp.371–380；IBM RJ6846, 1989）

- 一句话问题：ARIES/KVL 仍锁 key value（非唯一索引下粒度偏粗）、单记录操作锁数过高；改用「锁底层数据记录」的 data-only locking + WAL，把索引并发控制与恢复统一起来。
- 锁对象 / 粒度：不锁索引键本身，锁「key 中 RID 所指的底层数据」（记录级则锁 RID，页级则锁 RID 里的 pageID 部分），`index entry = <key, RID>`。原文：「A lock on a key is really a lock on the corresponding piece of data which contains the key. We call this data-only locking.」（PAGE 4）。next key 的锁同样落在下一条索引项的数据上。
- 冲突判定：Figure 2（PAGE 3）：FETCH & FETCH NEXT 在 current key 上 `S for commit duration`；INSERT 在 next key 上 `X for instant duration`、在 current key 上 `X for commit duration`（仅当 index-specific locking）；DELETE 在 next key 上 `X for commit duration`、在 current key 上 `X for instant duration`。与 03 的差别是这里用 X 而非 IX（data-only 下 next key 的锁就是记录锁）。
- 关键机制：① 三大并发来源（PAGE 1/PAGE 3–4）：data-only locking、SMO 期间也不加 commit-duration 索引页锁、检索/插入/删除可与 SMO 并发；② latching 只用页 latch，最多同时 2 个，持 latch 时不 unconditional 等锁，traversal 用 latch coupling（PAGE 4）；③ SMO 用 X tree latch 串行化、SM_Bit 标记未完成 SMO、`nested top action`（NTA）+ dummy CLR 使 SMO 不随用户事务回滚被撤销（PAGE 3、PAGE 7–8）；④ POSC（point of structural consistency）/ ROSI（region of structural inconsistency）/ Delete_Bit 保证重启 undo 时树可遍历（PAGE 8–9）；boundary key（页内最小/最大键）删除前须先建立 POSC（PAGE 6、PAGE 9）；⑤ EOF 特殊锁名（PAGE 5）；⑥ tripping point / wall 比喻与 insert-delete 不对称性（PAGE 7）；⑦ 结论中把 tree latch 换成 tree lock 以允许并发 SMO：叶级 SMO 取 `IX`，非叶级 SMO 升级为 `X`（PAGE 10）。
- 正确性：保证 RR / phantom protection（PAGE 4：「During the insert or delete of a key, a lock is requested on the next key currently in the index in order to support RR (thus solving the phantom problem)」）；Fetch not found 时也必须锁 next key（PAGE 5）。前提条件：记录管理器在 insert/delete 前已对底层数据取 commit-duration X 锁；conditional 锁请求在持有页 latch 时发出以保证推断的「存在/不存在」是已提交状态（PAGE 5）；锁等待后必须按 page_LSN 重校验（PAGE 5–6）。
- 代价：显著减少单记录操作锁数（PAGE 1「the number of locks acquired for even single record operations like record insert or delete is very high in System R」；PAGE 10「ARIES/IM reduces the number of locks for single-record operations by performing data-only locking rather than index-specific locking」）；支持 record/page 两种锁粒度。代价是假冲突：一把 rid 锁覆盖该记录在所有索引里的所有键值范围（16 PAGE 8–9 明确指出），以及为恢复付出的 SM_Bit / Delete_Bit / NTA / POSC 复杂度。latch「tens of instructions」vs lock「hundreds of instructions」（PAGE 9）。
- 与 RdmaRangeLock 的关系：v5 的「data-only 变体」，也是「锁对象命名」类别的代表；v2 latch coupling 与 SMO/latch 分离的来源。已实现：v5 已覆盖 next-key 语义；可补：把 `key_range` 的锁名从「键」换成「rid」的映射版本（单变量对比「同一棵 B+树、同一 workload，锁名解释不同」），以及 record-level vs page-level 粒度开关。

### 14 Hierarchical Locking in B-Tree Indexes（2007, G. Graefe, HP Labs；本 txt 为书籍 Chapter 2, pp.45–46 节选）

- 一句话问题：传统 B-tree 锁层次 `table/view → index/index partition → page or key` 在 TB 级库上「从整个索引直接跳到单页/单键」跨度太大，大扫描要么锁全索引、要么产生百万级锁；需在中间插入新的锁粒度，并用「有原则的层次锁」取代商用系统里那些反直觉的锁模式。

### 16 Key Range Locking Strategies for Improved Concurrency（1993, 19th VLDB, Dublin, pp.655–664）

- 一句话问题：常规锁管理器只会对「同名离散资源」做冲突检测，如何用它们实现 predicate locking 的受限形式（range locking），并在「并发度 vs 锁开销」之间系统性地取舍？
- 锁对象 / 粒度：三类资源 `range / key / record`，三种映射（PAGE 2）：① range 单独资源；② range 与 key 同一资源；③ range、key、record 三者同一资源。range 有两种：静态 `independent ranges`（PAGE 2–3，固定分区、无需索引）与 `key valued ranges`（PAGE 3，由现存相邻键值定义的 `(ki, ki+1]`，需索引维护有序键值表）。
- 冲突判定：MGL 兼容矩阵 Table 1（PAGE 2）；Table 3「maximum concurrency」给出操作对之间 Y/N 的目标矩阵（PAGE 4）；新模式的兼容矩阵 Table 6（PAGE 6）、KRL 复合模式兼容矩阵 Table 9（PAGE 7）。KRL 的判定规则是合取：「(RangeMode1, KeyMode1) is compatible with (RangeMode2, KeyMode2) if RangeMode1 is compatible with RangeMode2 and KeyMode1 is compatible with KeyMode2」（PAGE 7）。
- 关键机制：① 核心洞察「Because LMs are organized so as to detect conflicts only on specific named resources, key ranges must be uniquely named... by regarding index terms within indexes as defining ranges」（PAGE 1–2）；② 半开区间定义（PAGE 3）：`(ki, ki+1]` 用上界 `ki+1` 命名，「Note that we could also define our ranges as [ki, ki+1) and identify them by ki. To keep the ranges disjoint, one end must be open.」——正是 next-key / prior-key 的分叉点；③ 静态区间用 MGL：scan 用 S covering lock（「S range lock implicitly locks all records in the range. Explicit S record locks are not needed」，PAGE 3），update scan 用 SIX + 记录 X，单记录修改用 IX(range)+X(record) 或 X(range) 覆盖（PAGE 3）；④ key valued range 的难点是 insert/delete 会分裂/合并区间（PAGE 3–4）；Insert 4 步（PAGE 5）：instant `IX`「Next Range Lock」检查 `(ki-1, ki+1]`、`(ki-1, ki]` 取 IX commit、ki 键 X commit、若本事务原持有该 range 的 S/SIX 则传播为 SIX（「SIX is the least upper bound for (SIX, S) and IX」）；Delete 3 步（PAGE 5）：ki 记录 X commit、`(ki-1, ki]` SIX instant、合并后的 `(ki-1, ki+1]` SIX commit（delete range）；⑤ 三个新 intention 模式（PAGE 5–6）`IU / IIn / ID`（Intention Update / Insert / Delete），「We made the intention lock modes operation specific. Then we constructed the lock mode compatibility table to directly correspond to the exclusion and compatibility needed by each operation」，避免用过度严格的 SIX 保护 delete range；⑥ ARIES/KVL（PAGE 6）：「The best locking protocol for range locking using existing MGL lock modes is ARIES/KVL. It does not distinguish range from key lock modes」，insert 用较弱的 IX 使 insert-in-front-of-insert 可行，delete 用 X next key lock；合并 range+record 的代价是「prevent inserts in front of Read Single and Update Single」；⑦ KRL 复合模式（PAGE 7）：`(RangeMode, KeyMode)`，8 种实际模式（笛卡尔积 18 去掉不出现/兼容相同的组合），Table 8 给出 Current Key / Next Key 的锁表（Read: IS-S；Update: IU-X；Insert: IIn-X + IIn- instant on next；Delete: X instant on current + ID-(S,SIX,X) on next；Scan: S/X）；KRL 相对 ARIES/KVL 额外允许「Inserts in front of singleton reads and updates」「Deletes in front of singleton reads and updates」（PAGE 8）；⑧ 三资源合一 = ARIES/IM（PAGE 8–9）：「ARIES/IM uses a lock on a record identifier instead of a key value lock as the way to lock a range. ### 36 The Notions of Consistency and Predicate Locks in a Database System（1976, CACM 19(11), pp.624–633）

- 一句话问题：把「事务/一致性/调度」形式化，证明 2PL 正确的充要条件，并指出关系数据库按值寻址会产生 phantom，必须锁「逻辑子集」而非物理记录，进而提出谓词锁。
- 锁对象 / 粒度：`predicate lock (R, P, a)`，P 是定义在关系 R 元组上的 admissible predicate（对给定元组可有效判定真假），`a ∈ {read, write}`；一个 access 等价于「对笛卡尔积中所有满足 P 的元组的动作集合」（可能是无限集）。退化形式：P = TRUE 锁整个关系，P(t) 仅对某元组为真即锁单个元组（PAGE 6、PAGE 10）。另有 field-level predicate lock 的推广（PAGE 8–9）。
- 冲突判定：形式化定义（PAGE 8）：动作 `(R,t,a)` 满足锁 `(R',P',a')` iff `R=R'` 且 `P'(t)=TRUE` 且 `a=a' or a'=write`；动作与锁冲突 iff `R=R'` 且 `P'(t)=TRUE` 且 `a=write or a'=write`。两把谓词锁冲突 iff 存在某动作满足其一而被另一禁止；落到「simple predicate」上（PAGE 9）：`R≠R'` 无冲突；两者都不是 write 无冲突；否则看 `P ∧ P'` 是否可满足。判定方法是把 `P ∧ P'` 化为 DNF，逐合取支检查原子谓词是否矛盾（PAGE 10）。
- 关键机制：① 2PL 正确性证明（PAGE 4–5）：well-formed + two-phase ⇒ 任何 legal schedule consistent（8d），反之不成立（8e）；用 `SHRINK(Ti)`（首次 unlock 步）构造全序证明；② phantom 定义（PAGE 6）：「If the tuple does not exist, "it" should be locked to insure that no other transaction will create such a tuple before the first transaction terminates. In this case the "nonexistence" of the tuple is being locked. Such nonexistent tuples are called phantoms.」；③ 「a transaction needs to lock a logical rather than a physical subset of the database. These subsets may be specified by predicates」（PAGE 1 abstract）；④ 一般谓词的可满足性「recursively unsolvable (Kleene)」（PAGE 7），因此限制为 `simple predicate`：atomic predicate 为 `(field name) {<,=,>} (constant)` 的布尔组合（PAGE 9）；⑤ LOCK 表实现：事务名 ↔ 谓词锁的二元关系，`YES = {(T,L) ∈ LOCK | A satisfies L and T = T*}`，YES 为空则事务 not well-formed（PAGE 9）；⑥ 覆盖谓词：「If the desired set is not describable by a simple predicate then any "larger" simple predicate... will be a suitable predicate for the lock」（PAGE 10）；访问必须被「单个谓词锁」覆盖，或放松为「被事务所持锁的并集覆盖」（PAGE 8）；⑦ 字段级推广（PAGE 8–9）与 IMS 子树 / DBTG set 的类比（PAGE 10）。
- 正确性：(13b)「If transaction T locks predicate P on relation R, then for any tuple t in the Cartesian product underlying R such that P(t) = TRUE, no other transaction may insert, delete or modify t until T releases the predicate lock. That is, predicate locks solve the problem of phantoms.」（PAGE 9）。前提：所有事务 well-formed + two-phase；scheduler 强制该规则（PAGE 9「(13a) All transactions are well-formed and two-phase」）；只允许 simple predicates。
- 代价：冲突判定不可解 → 必须限制谓词类；即便 simple predicate 也要做 DNF 转换与逐支可满足性检查，「much more complicated」且「not efficient」（PAGE 3 讲义的对应评价、PAGE 9 本文）；与「只按同名锁做哈希查找」的传统 LM 形成鲜明对比（11 PAGE 4、03 PAGE 6、16 PAGE 9 都引用这一点作为不实现纯谓词锁的理由）。LOCK 表是谓词列表而非哈希键，无法 O(1) 查冲突。
- 与 RdmaRangeLock 的关系：本组理论源头与 `predicate` 版本的直接对应物；`exact-range` 就是 simple predicate（`lo ≤ key < hi` 的原子不等式布尔组合）的精确可判定实例。已实现：`predicate`（整段区间锁）、`exact-range`（精确 `[lo,hi)`）、以及 `detect_conflict(other)` 的「区间相交且至少一写」语义；可补：多谓词 DNF 可满足性判定、覆盖谓词（用更大区间近似复杂谓词）、field-level 分量锁。
- 可复现性：现有 `lock(mode, key_range)` 已能表达 simple predicate 中的一维区间类（`key_range=[lo,hi)`）；若要把「任意布尔组合」作为一个单变量版本，需新增：谓词解析 + DNF + 原子矛盾检查的 `detect_conflict`（不再是 `key_range` 而是 `predicate` 对象），以及覆盖谓词放大策略。单变量自变量：谓词表达能力（单区间 / 多区间布尔组合 / 任意 simple predicate）。
- 关键原文证据：
  - PAGE 1 abstract：「Consistency requires that a transaction cannot request new locks after releasing a lock. Then it is argued that a transaction needs to lock a logical rather than a physical subset of the database. These subsets may be specified by predicates. An implementation of predicate locks which satisfies the consistency condition is suggested.」
  - PAGE 6：「If the tuple does not exist, "it" should be locked to insure that no other transaction will create such a tuple before the first transaction terminates. In this case the "nonexistence" of the tuple is being locked. Such nonexistent tuples are called phantoms.」
  - PAGE 7：「the controller must compare the requested predicate lock against the outstanding predicate locks of other transactions on this relation. If two such predicates are mutually satisfiable (i.e. have an existing or phantom tuple in common), then there is conflict and the request must wait or preempt; otherwise, the request can be granted immediately.」
  - PAGE 9：「In general this is a recursively unsolvable problem (even if predicates are restricted to using the arithmetic operators +,·,−,÷ as shown by Gödel)... We propose the following simple class of predicates. A simple predicate is any Boolean combination of atomic predicates.」「(13b) ... That is, predicate locks solve the problem of phantoms.」
  - PAGE 10：「The procedure is to organize P ∧ P' of case (c) into disjunctive normal form (Kleene) and then for each disjunct see whether it is satisfiable or not.」「If the desired set is not describable by a simple predicate then any "larger" simple predicate... will be a suitable predicate for the lock.」

### 41 A Critique of ANSI SQL Isolation Levels（1995, ACM SIGMOD'95；01 的清晰 OCR 副本）

- 一句话问题：与 01 完全相同（同一篇论文的两个抽取副本），本副本 OCR 干净，适合作为引文与表格的权威来源。
- 锁对象 / 粒度：同 01，`data item` 与 `predicate`（含 phantom 的无限集合），`item lock (record lock) is a predicate lock where the predicate names the specific record`（PAGE 3）。
- 冲突判定：同 01，「Two predicate locks by different transactions conflict if one is a Write lock and if there is a (possibly phantom) data item covered by both locks」（PAGE 3）。
- 关键机制：同 01，但本副本的 Table 1/2/3/4 排版完整可读：Table 2（PAGE 4）Degree 3 = `Long duration Read locks (both)` + `Long duration Write locks`；Locking REPEATABLE READ = `Long duration data-item Read locks` + `Short duration Read Predicate locks`；Table 3（PAGE 6）四现象 P0/P1/P2/P3 定义的隔离级别矩阵；Table 4（PAGE 10）各隔离级别允许的异常总表。P3 的 loose 定义（PAGE 6）：`r1[P]...w2[y in P]...(c1 or a1)`，并明确「the definition of P3 above prohibits any write satisfying the predicate once the predicate has been read — the write could be an insert, update, or delete」。
- 正确性：同 01；PAGE 6「Prohibiting P3 means long-term Read predicate locks」、Remark 6 锁定义与现象定义等价；PAGE 8「Remark 10. Snapshot Isolation histories preclude anomalies A1, A2 and A3... ANOMALY SERIALIZABLE « SNAPSHOT ISOLATION.」以及「However, Snapshot Isolation does not preclude P3」。
- 代价：同 01；Table 2 的 short/long duration 维度是最适合做单变量的分类轴。
- 与 RdmaRangeLock 的关系：同 01，作为「防幻读判据」与「锁持续时间」章节的主要引文源；建议在报告中统一引用本副本（41）的 PAGE 号，并把 01 标注为 OCR 劣化副本。
- 可复现性：同 01。建议在 workload 生成器里实现四个 history 模式 `P0/P1/P2/P3`，验证 v3（短谓词读锁）会出现 P3、v4/v5/v6/long predicate 不出现；SI 按用户口径不建版本。
- 关键原文证据：
  - PAGE 3：「A Read (resp. Write) predicate lock on a set of data items determined by a given `<search condition>` is effectively a lock on all data items satisfying the `<search condition>`. This may be an infinite set, as it includes data present in the database and also all phantom data items...」「Two predicate locks by different transactions conflict if one is a Write lock and if there is a (possibly phantom) data item covered by both locks. An item lock (record lock) is a predicate lock where the predicate names the specific record.」
  - PAGE 4 Table 2：「Degree 3 = Locking SERIALIZABLE / Well-formed Reads / Long duration Read locks (both) / Well-formed Writes, Long duration Write locks」；「Locking REPEATABLE READ / Long duration data-item Read locks / Short duration Read Predicate locks」。
  - PAGE 6：「Prohibiting P3 means long-term Read predicate locks.」「Remark 6. The locking isolation levels of Table 2 and the phenomenological definitions of Table 3 are equivalent. Put another way, P0, P1, P2, and P3 are disguised redefinition's of Locking behavior.」
  - PAGE 8：「Snapshot Isolation has no phantoms (in the strict sense of the ANSI definitions A3). Each transaction never sees the updates of concurrent transactions.」「However, Snapshot Isolation does not preclude P3.」

## 本组发展史时间线

- **1976 · Eswaran / Gray / Lorie / Traiger（36）**：提出 phantom 与谓词锁，证明「well-formed + two-phase ⇒ 一致调度」，并因谓词可满足性不可判定而把锁限制为 simple predicate + DNF 判定——本组全部工作的理论起点。
- **1976/1977 · Gray / Lorie / Putzolu / Traiger（13）**：把谓词锁工程化为「index interval locks / 每个 index key value 作为可锁对象」，同时发明六模式多粒度意向锁（IS/IX/S/SIX/X）与 0–3 级一致性，System R 首次落地「用键值锁防 phantom」。
- **1976–1981 · System R（未正式发表，由 03/23 追述）**：首个支持 key-value locking + RR 的系统，用 next-key S/X 锁，但产生 adjacent key conflict problem 与页锁死锁，成为后续所有「修正」的靶子。
- **1990 · Mohan, ARIES/KVL（03）**：修正 System R——把原本表级用的 IX/SIX 引入键值锁、insert 的 next-key 改为 instant duration、引入 lock state replication / EOF 哨兵 / latch-lock 分离 / SM-Bit，明确「range locking via next key locking」。
- **1992 · Mohan & Levine, ARIES/IM（04）**：再修正——锁对象从 key value 换为底层记录（data-only locking），单记录操作锁数大幅下降，并用 WAL + nested top action 解决 SMO 与恢复的交互。
- **1993 · Lomet（16）**：把前两者系统化为一个「资源映射 × 锁模式」设计空间，指出 ARIES/KVL 合并 range+key 的并发损失、ARIES/IM 合并三者的更大损失，提出 IU/IIn/ID 与 KRL 复合模式达到 Table 3 的最大并发。
- **1995 · Berenson / Bernstein / Gray / Melton / O'Neil & O'Neil（01/41）**：从标准侧修正口径——把 P3 严格化为「禁止任何满足谓词的写」，证明 Locking SERIALIZABLE 必须持长谓词读锁，并给出 Snapshot Isolation 的严格定义（本项目据此把 MVCC/SSI 排除出实现类别、只保留判据）。
- **1999 · Mohan（23）**：回顾并固化 ARIES 家族分类（KVL = key value vs IM = individual index entry / data-only），列出索引并发控制必须回答的 11 个问题，把「高效锁 not found 条件」列为公开问题。
- **2007 · Graefe（14，另见 02 §1.1）**：把层次锁「更严格地」用到 keys 与 gaps，提出 separator-key / key-prefix 两种新锁层次、ghost records、组合模式，目标是去掉商用系统里的 counter-intuitive lock modes，并支持在线增删锁层次与 escalation/de-escalation。
- **2010 · Graefe（02）**：综述统一框架——结构保护（latch，线程）与内容保护（lock，事务）二分，明确 key range locking 是 predicate locking 的特例、next-key 与 prior-key 同类、instant lock = test-without-set、`+∞`/`NULL` 哨兵、ghost/fence 与组合模式，给出「neither pure predicate locking nor precision locking has been adopted in major products」的工程结论。
- **2010 / 2026 · Microsoft Learn（21 / 22）**：把上述理论工程化为 SQL Server 的 `RangeS-S / RangeS-U / RangeI-N / RangeX-X` 与 conversion 锁、`n+1` 锁计数、`KEY` 资源类型与 sp_lock 可观测模式清单，补充「SERIALIZABLE + 索引覆盖谓词」这一常被忽略的前提。
- **2012 · Fekete（11）**：教学化收束因果链，点明「Predicate Locking... Never implemented in any system I know of」、ARIES/KVL 的「S-lock on key k implicitly locks (k0,k]」、InnoDB 的 `G` gap 模式，并把 latch coupling / system transaction / multi-level reasoning 纳入同一叙事。

## 本组建议的可复现类别

> 划分准则：同一类别内的命名方案共享不变式、可用同一棵 B+树与同一 workload、差别只体现在 `lock(mode, key_range)` 的一个（或一组可枚举的）自变量上，因此**应实现为一个版本加参数开关**，而不是多个独立版本；类别之间才需要不同的实现骨架。已按用户口径把 gap-lock 与 next-key-lock 归入同一类，且不把 MVCC/SSI 列为类别。

**[REPRO-1] 整段区间 / 谓词覆盖锁（一次范围操作一把区间锁）**
- 包含哪些命名方案：Eswaran'76 predicate lock（36，simple predicate + DNF 可满足性）、Berenson'95 的 `<search condition>` 谓词读锁（01/41 PAGE 3）、Gray'76 的 index interval locks（13 PAGE 10）、Lomet'93 的 independent/fixed ranges + MGL covering S/X（16 §2.2）、RdmaRangeLock 已实现的 `predicate` 与 `exact-range`（`[lo,hi)`）、SQL Server 的 PAGLOCK/TABLOCK 粗粒度退化（21 PAGE 6）。
- 共享不变式：一把锁覆盖整个查询区间；冲突 ⟺ 区间相交且至少一个为写；区间边界不依赖「当前存在的键」，或只依赖静态分区；`detect_conflict(other)` 为区间交判定（本项目已具备）。
- 可测的自变量：区间宽度 / 键分布偏斜（尤其右端单调递增插入热点）/ 读写比 / 谓词表达能力（单区间 vs 布尔组合）。
- 预计能观察到的差异：锁数恒为 O(1) 每查询、`get_lock_count()` 最低；假冲突随区间宽度近似线性增长，在高偏斜插入热点下吞吐骤降；对比 [REPRO-2] 可量化「用邻接键细分换来的并发增益」。`exact-range` 相对 `predicate` 应显示边界放大带来的假冲突下降。

**[REPRO-2] 邻接键区间锁（gap / next-key / prior-key / ARIES-KVL / ARIES/IM / SQL Server key-range 同属一类）**
- 包含哪些命名方案：InnoDB `G` gap 模式（11 PAGE 6）、next-key locking（03「range locking via next key locking」、23 PAGE 9–10）、prior-key locking（02 PAGE 14、16 PAGE 3 的 `[ki,ki+1)`）、ARIES/KVL 的 key value lock（03、16 §4.1.1）、ARIES/IM 的 data-only next-key X lock（04 Figure 2）、System R 的 adjacent key（03 PAGE 13）、SQL Server `RangeS-S/RangeS-U/RangeI-N/RangeX-X`（21/22）、Lomet KRL（16 §4.1.2）、以及「范围由现存键命名」的所有变体。
- 共享不变式：区间由「当前存在的一个键值」命名，锁覆盖 `(前驱, 键]` 或 `[键, 后继)`；一端必须开区间（16 PAGE 3「To keep the ranges disjoint, one end must be open」）；插入必须先在 next key 上做 instant 冲突检查；删除必须在 next key 上留 commit-duration 强锁（23 PAGE 10「the next key lock during an insert is only a check (instant lock), the one during deletion must be a lock which is held until commit」）；右/左边界用 `+∞` / `NULL` / `EOF` 特殊锁名处理（02 PAGE 14、03 PAGE 7、04 PAGE 5）；区间分裂/合并时须把已有锁传播到新区间（16 §3.3、02 PAGE 17）。
- 可测的自变量：① 方向 next-key vs prior-key；② next-key 锁持续时间 instant vs commit；③ 是否区分 range 与 key 为两个分量（简单 S/X vs 复合 RangeT-K）；④ 是否启用 ghost/fence 消除跨页找 next key；⑤ 唯一键 vs 非唯一键。
- 预计能观察到的差异：next-key 在右端单调插入时所有插入撞 `+∞` 哨兵而串行，prior-key 用 `NULL` 避开（02 PAGE 14–15）；instant 锁不占锁表存储、不延长 hash 链（03 PAGE 12），但严格 2PL 被破坏、正确性依赖「单次页 latch 覆盖检查+插入」；复合模式（21/16 KRL）在 `get_lock_count()` 相近时冲突率显著低于简单 S/X；SQL Server 的 `n+1` 锁计数可直接与 v4/v5 对比（21 PAGE 5）。

**[REPRO-3] 层次 / 多粒度锁（意向模式与复合模式）**
- 包含哪些命名方案：Gray'76 六模式 `NL/IS/IX/S/SIX/X`（13 PAGE 4）、Lomet'93 静态区间上的 MGL（16 §2.2）、KRL 复合 `(RangeMode, KeyMode)` 与 `IU/IIn/ID`（16 §3.4/§4.1.2）、Graefe 层次化 key range locking 的 `SN/NS/XS` 组合模式（02 §5.3 Figure 8）、14 的三种层次（index→leaf→key range、separator keys、key prefixes）与 escalation/de-escalation、SQL Server 的 `IS/IU/IX/SIU/SIX/UIX`（22 PAGE 4）、ARIES/KVL 把 IX/SIX 用于键值（03）、04 结论里 tree lock `IX→X` 升级。
- 共享不变式：`mode` 是若干逻辑分量（意向 vs 绝对、range vs key、或父子粒度）的复合；兼容判定 = 各分量兼容的合取（16 PAGE 7、02 PAGE 19「XS is compatible with NS because X is compatible with N and S is compatible with S」）；加锁顺序 root-to-leaf、释放 leaf-to-root 或全持到 EOT（13 PAGE 5）；用「更多模式数」换「更少 lock manager 调用数」。
- 可测的自变量：模式集合规模（2 / 6 / 8 / 组合模式）、是否启用 escalation/de-escalation 及其阈值、区间层级数、是否区分 range 与 key 两个资源 id。
- 预计能观察到的差异：并发度与锁表条目数的权衡曲线（16 PAGE 2「range+key 合并不损失并发，把 record 也合并才损失并发」）；一次 escalation 可把并发度压到 1（14 PAGE 2）；每锁 64–128 bytes、每锁数千 CPU cycles 的内存/CPU 数量级（14 PAGE 2）可被 `get_lock_count()` 与本地矩阵复现；跨主机 RDMA 矩阵下模式数增加会放大 `detect_conflict` 的往返/字节开销。

**[REPRO-4] 锁对象命名 / 资源映射（key value vs index entry vs RID）**
- 包含哪些命名方案：ARIES/KVL 的 index-specific key value locking（03、23 PAGE 9）、ARIES/IM 的 data-only locking（04、23 PAGE 9）、`indexID + RID` 前缀的 index-specific 变体（23 PAGE 9）、Lomet 的三种资源映射（16 §1.3）、`<key,rid>` 排序的非唯一键方案（16 §5.3、02 §5.4）、SQL Server `KEY` 资源类型与 `IndId`（22 PAGE 2）。
- 共享不变式：每把锁映射到一个可哈希的定长锁名；范围语义由「锁名如何解释」决定，而非由锁表结构决定；`lock(mode, key_range)` 的 `key_range` 可以是键区间，也可以是「该区间内记录的 RID 集合」。
- 可测的自变量：锁名 = `hash(key)` / `hash(rid)` / `indexID+hash(rid)` / `hash(<key,rid>)`；锁粒度 record vs page；唯一键 vs 非唯一键；索引数量（单索引 vs 多索引 DAG）。
- 预计能观察到的差异：ARIES/IM 单记录操作锁数显著低于 KVL（04 PAGE 1/10），但一把 rid 锁覆盖所有未参与扫描的索引范围 → 假冲突上升（16 PAGE 8–9「preventing phantoms in key value ranges that do not participate in the scan」）；非唯一索引下 key value 锁一次锁住整个 duplicate cluster（23 PAGE 9、02 §5.4）；多索引时 KVL 需对所有路径加锁而 data-only 只需一把。

**[REPRO-5] 工程机制开关（instant / ghost / 边界哨兵 / 重校验）**
- 包含哪些命名方案：`instant duration lock` = test-without-set（03 PAGE 3、02 PAGE 14、11 PAGE 6、16 PAGE 5、21 `RangeI-N`）、`lock state replication via next key locking`（03 PAGE 10）、ghost/pseudodeleted 记录与 fence keys（02 §5.2、16 §5.4、14 PAGE 1）、EOF / `+∞` / `NULL` 哨兵（03 PAGE 7、04 PAGE 5、02 PAGE 14）、`revalidation after unconditional locking` + VN / page_LSN（03 PAGE 5/8、04 PAGE 5、02 PAGE 15）、SM_Bit / tree latch / nested top action（03/04）、Commit_LSN 无争用跳过加锁（23 PAGE 12）。
- 共享不变式：这些不是独立的锁粒度类别，而是叠加在 [REPRO-2]/[REPRO-3] 上的正确性/开销开关；共同前提是「latch 保护结构、lock 保护内容」，且「持 latch 时不 unconditional 等锁」（23 PAGE 8 三条规则、04 PAGE 4）。
- 可测的自变量：instant vs commit duration；ghost on/off；fence key on/off；哨兵存在与否；是否允许违反严格 2PL 的短锁。
- 预计能观察到的差异：ghost 让删除只需锁 key 不需邻 gap、避免回滚时空间分配失败（02 PAGE 15–16）；fence key 消除「跨页找 next key」的额外往返，对 RDMA 矩阵收益最大；instant 锁降低锁表占用但把正确性押在单次 latch 临界区上（02 PAGE 15）；去掉 `+∞`/`EOF` 哨兵后，右端边界查询应出现 P3/A3 幻读——这是本项目「防幻读」回归测试最该补的一档。
