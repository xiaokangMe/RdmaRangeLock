### 07 CockroachDB「Serializable, Lockless, Distributed」博客（2016, Cockroach Labs Blog, Matt Tracy, 2016-05-04）

- 一句话问题：在无中心节点的分布式 KV 上，能否完全不加锁、仅靠时间戳排序 + 中止就得到可串行化且可恢复的执行？
- 保护对象 / 粒度：**读键 / 读区间 → 时间戳**（timestamp cache 的 key 是 key range）；写意图（write intent）保护单键的未提交值。范围读时**整个扫描区间**作为一个条目登记。
- 冲突/异常判定：**可串行化图无环判定**（"a history is guaranteed to be serializable if (and only if) its serializability graph is acyclic"，PAGE 5）。三类冲突 RW / WR / WW；规则是「只允许操作与更早时间戳冲突，凡会让提交产生指向更晚时间戳的冲突者，一律中止并以更晚时间戳重启」（PAGE 6）。可恢复性由 **strict scheduling** 保证：操作只能读写已提交值（PAGE 9）。
- 关键机制：①每事务在起始节点取一个**时间戳**，MVCC 按 `key → 多个时间戳版本` 存储，读只返回低于自身时间戳的最新版本（PAGE 6–7），因此 WR 冲突不可能指向更晚事务。②**Read Timestamp Cache（PAGE 7–8）**：每次读把读时间戳记入节点本地 cache；写前查 cache，若返回时间戳 > 写时间戳则中止重启。cache 是 **interval cache（key 即 key range）**，谓词/scan 会把「整个被扫描的 key range」写进去，专门阻断「写入一个当时扫描时不存在的 key」的 RW 冲突——这就是**防幻读的范围标记**；cache 是内存受限 LRU，被淘汰的键用 **low water mark**（cache 中最早的读时间戳）兜底。③WW 冲突：只能写 key 的最新版本，若已有更晚版本则中止。④未提交值以 **write intent**（MVCC 记录 + 指向 transaction record 的指针，排序紧邻最新已提交值之前）暂存（PAGE 9–10）；遇到 intent 时走 **push**：按 priority 确定性中止（低优先级败；优先级相等则高时间戳败；都相等则 pusher 败），重启优先级取 `max(randomInt(), 造成重启者优先级 − 1)` 逐步抬升（PAGE 10–11）；transaction record 带 **heartbeat**，过期即视为 abandoned（PAGE 12）。
- 正确性：防幻读（范围进 timestamp cache）、防写偏斜（RW 冲突被时间戳排序拒掉）、无漏报（acyclic 图充分必要）；**假阳性有明显来源**：low water mark 与 LRU 淘汰都会把无关的晚时间戳强加给写者，导致本可提交的事务被推后/中止。依赖前提：节点本地 HLC 时间戳、MVCC 多版本、事务可重启、无中心 oracle（PAGE 3 明列 Distributed: no central oracle）。
- 代价：内存 = timestamp cache（LRU 有界）+ 每键多版本 + intent/transaction record；中止率随「读后写」竞争上升；往返 = 分布式提交 + push 查询 transaction record；**需要节点时钟但不需要全局中心时钟/中心节点**（编辑器注 PAGE 2 声明此文描述的是 pre-1.0 旧「lockless」设计，新版已加更多锁）。
- 与 RdmaRangeLock 的关系：**本组最接近「非阻塞读范围标记」的一篇**——`interval cache` 的 `key range → high-water read timestamp` 与 `lock(mode, key_range)` 的粒度完全同构，`detect_conflict()` 可对应「写键是否落在已登记范围且时间戳更晚」。但要落地必须引入 **MVCC 多版本 + 每事务时间戳 + 事务可中止重启** 三层前提；只要保留「单版本 + 严格 2PL」，写一旦覆盖旧值就无法在提交时再判定，故**不能直接兼容**。
- 可复现性：**可做近似对照，但需引入时间戳层**。最小改动：保留 `lock/unlock_all/get_lock_count/detect_conflict` 与单版本 B+树；给全局加一个单调计数器当「事务时间戳」；把 `lock(S, range)` 从「加读锁」改成「在 range 上登记 `read_ts`（不阻塞）」；`lock(X, key)` 时若 key 命中某个 range 且 `write_ts < read_ts`，则 `detect_conflict()` 返回 true 并**中止写者**（代替阻塞）。这不引入版本、不引入时钟，只是把「阻塞」换成「登记 + 写时检查 + 中止」，已在语义上离开严格 2PL，但可作为「非阻塞范围标记」的 v-对照版。
- 关键原文证据：PAGE 7–8："The timestamp cache is an interval cache, meaning that its keys are actually key ranges. If a read operation is actually a predicate operating over a range of keys (such as a scan), **then the entire scanned key range is written to the timestamp cache. This prevents RW conflicts where the key being written was not present during the scan operation.**"；PAGE 3："**Lockless**: Operations execute without taking locks on resources. Correctness is enforced by aborting transactions which would violate either serializability or strict scheduling."

### 08 CockroachDB Transaction Layer 架构文档（在线文档，抓取 2026-11-07, docs.cockroachlabs.com/architecture/transaction-layer）

- 一句话问题：现代（已加回锁的）CockroachDB 事务层如何把「时间戳缓存 + 写意图 + 每节点锁表 + HLC」组合成 SERIALIZABLE，并兼顾只读/陈旧读的低延迟？
- 保护对象 / 粒度：**timestamp cache（读 high-water mark，区间语义）** + **write intent / per-node lock table（单键，复制的排他锁 + 未复制的共享锁）** + **closed timestamp（range 级「此时间戳以下不再有写」承诺）**。写集合由 TxnCoordSender「tracking each written key or key range」（PAGE 9）。
- 冲突/异常判定：**write-after-read 冲突由 timestamp cache 判定**（PAGE 17："Write after read, when a write with a lower timestamp encounters a later read. This is handled through the timestamp cache."）；**read refreshing** 在提交时验证读集未被改动（PAGE 18）。四类冲突：write-write、write-read、**write after read**、read within uncertainty window（PAGE 16–17）。
- 关键机制：①**timestamp cache**：读即记时间戳（high-water mark），写时若写时间戳早于 cache 最新值则**把事务时间戳 push 到更晚**（PAGE 5–6）。②**read refreshing（PAGE 18）**：事务时间戳被 push 后，用 `RefreshRequest` 重查「原时间戳到 push 后时间戳之间所有读过的 key 有无写入」，失败（read invalidation）则重试；READ COMMITTED 不做此检查。③**HLC（hybrid-logical clock，PAGE 4–5）**：物理 + 逻辑分量，网关节点为事务取 HLC 时间戳，节点间请求携带 HLC 以保序；max clock offset 超限即崩溃（PAGE 5）。④**write intent**（复制的锁 + 临时值）与 **concurrency manager = latch manager + per-node in-memory lock table**（PAGE 10–14）：latch 只覆盖单个请求，lock table 的锁存活到事务结束，FIFO 排队；intents 存于 MVCC keyspace，evaluation 时才被发现并纳入 lock table。⑤**TxnWaitQueue**（PAGE 17）+ 优先级 push + 死锁随机中止。⑥**closed timestamps / Follower Reads**（PAGE 6–8）。⑦**non-blocking transactions（PAGE 26–27）**：靠「半同步时钟的有界不确定性」而非节点间通信，写时间戳被推到未来 + **commit-wait**。⑧Parallel Commits（STAGING / InFlightWrites，PAGE 20–24）、buffered writes（PAGE 24–25）。
- 正确性：SERIALIZABLE 下防幻读/写偏斜（论文 PAGE 15 明说演示 write skew 预防）；**假阳性**来自 timestamp cache/closed timestamp 推高时间戳与 read invalidation；依赖前提：HLC 时钟同步（80% 偏移即崩）、MVCC、客户端重试逻辑（PAGE 15 "transaction restarts / client-side retry handling"）、2PC/Raft 复制。
- 代价：内存 = timestamp cache + lock table + intent + TxnWaitQueue；往返 = Parallel Commits 把提交往返从 2 轮共识降到 1 轮（PAGE 20）、buffered writes 减少网关↔leaseholder 往返；**不需要全局中心时钟/中心节点，但需要 HLC + NTP + max clock offset 强制**；read refreshing 使长事务中止率随时钟推进上升（PAGE 7–8）。
- 与 RdmaRangeLock 的关系：与 07 同源但**明确回退到「用锁」**（编辑器注已在新版出现 lock table / exclusive & shared locks / SELECT FOR UPDATE），恰好构成一条反面证据：**纯非阻塞方案在生产里被加回了阻塞锁与中心化 lock table**。可作为「范围标记 → 后退到阻塞锁」的演化对照；其 `timestamp cache` 仍是最容易折算的「非阻塞读范围标记」。需要引入的前提同 07（MVCC + 时间戳 + 提交时验证/中止）。
- 可复现性：同 07，可做「timestamp cache 近似版」；但 **read refreshing / HLC / commit-wait / Follower Reads 在单版本 2PL 下不可复现**（需要版本链与时钟）。最小可复现子集仍是「range → read_ts 标记 + 写时检查 + 中止」。
- 关键原文证据：PAGE 5："Whenever an operation reads a value, CockroachDB stores the operation's timestamp in a **timestamp cache, which shows the high-water mark for values being read**."；PAGE 6："Whenever a write occurs, its timestamp is checked against the timestamp cache. If the timestamp is earlier than the timestamp cache's latest value, CockroachDB will attempt to **push the timestamp for its transaction forward** to a later time."；PAGE 18："any values which the transaction previously read must be checked to verify that no writes have subsequently occurred between the original transaction timestamp and the pushed transaction timestamp. **This check prevents serializability violation.**"

### 09 Spanner: Google's Globally-Distributed Database（2012, OSDI '12, Corbett et al.）

- 一句话问题：全球分布、同步复制的数据库如何用「暴露时钟不确定性的 TrueTime」给出外部一致（linearizable）事务，并做到**无锁只读事务**？
- 保护对象 / 粒度：**lock table 把「ranges of keys」映射到 lock states**（PAGE 3，这就是范围级锁状态）；只读事务用**全局提交时间戳 + scope expression（概括整个事务将读的 keys）**；细粒度扩展把 **key ranges → prepared-transaction timestamps / commit timestamps**（PAGE 9）。
- 冲突/异常判定：**外部一致性不变式**（PAGE 7）：`t_abs(e_commit1) < t_abs(e_start2) ⇒ s1 < s2`，由 **Start 规则**（`si ≥ TT.now().latest`，在 `e_server_i` 之后取）与 **Commit Wait 规则**（客户端看到 Ti 的数据前必须 `TT.after(si)` 为真）两条共同保证，并附传递性证明（PAGE 7）。读写事务用 **2PL + wound-wait 防死锁**（PAGE 8）。
- 关键机制：①**TrueTime API**（PAGE 5）：`TT.now()` 返回 `TTinterval [earliest, latest]`，`TT.after(t)` / `TT.before(t)`；底层用 GPS + 原子钟（Armageddon masters），Marzullo 算法剔除说谎者，ϵ 为锯齿（1–7 ms，均值约 4 ms，轮询 30 s，漂移 200 µs/s）。②**读写事务**（PAGE 7–8）：client 缓冲写，读时取读锁并用 **wound-wait** 避免死锁；2PC over Paxos，参与者选 prepare timestamp，协调者取 `s ≥ 所有 prepare ts、≥ TT.now().latest、≥ 已分配过的 ts`，**commit-wait 至少 2·ϵ**（PAGE 8）后才让副本应用并释放锁。③**只读事务**（PAGE 6, 8）：预声明无写，在系统选定时间戳 `s_read` 上以 snapshot read 执行、**不加锁、不阻塞写**、可在任意足够新的副本读；单 Paxos group 用 `LastTS()`，多 group 用 `TT.now().latest`；**scope expression** 概括将读的 keys（PAGE 8）。④**safe time** `t_safe = min(t_Paxos_safe, t_TM_safe)`，`t_TM_safe = min_i(s_prepare_i,g) − 1`（PAGE 7）；§4.2.4 细化（PAGE 9）用 **key ranges → prepared-transaction timestamps** 的细粒度映射消除假冲突，`LastTS()` 也可用 **key ranges → commit timestamps** 细化。⑤Paxos leader lease 不相交不变式 + `MinNextTS(n)`（PAGE 9, 13–14）。
- 正确性：外部一致性 + 无锁只读事务（无幻读、无阻塞）；**假阳性**来自粗粒度 `t_TM_safe`（单个 prepared 事务阻塞所有更晚读）与 `LastTS()`，PAGE 9 明确用 key-range 细粒度映射消除；依赖前提：TrueTime 有界 ϵ（GPS/原子钟硬件）、2PC over Paxos、单调时间戳与 lease 不相交。
- 代价：内存 = lock table（range→state）+ 多版本 + safe time 映射；往返 = commit-wait（≥ 2ϵ，约 5 ms，PAGE 9–10 实测）、2PC、Paxos、多 group 的 `s_read` 协商；**需要全局时钟基础设施（TrueTime），且有中心化角色（universe master / placement driver 为 singleton，PAGE 2）**；只读事务不阻塞写但可能等 safe time 推进。
- 与 RdmaRangeLock 的关系：**「范围 → 锁状态 / 时间戳」的直接源头**（PAGE 3 的 lock table maps ranges of keys to lock states；PAGE 9 的 key ranges → timestamps 细粒度映射），与 `lock(mode, key_range)` 同构。但 Spanner 的读写事务**本来就是阻塞 2PL**，只有只读事务靠 MVCC 快照无锁；因此它更适合作「**阻塞范围锁 + scope 摘要**」的粒度对照，而非「非阻塞标记」对照。要移植需引入：全局时间戳（可用单节点单调计数器近似替代 TrueTime）、多版本快照、commit-wait。
- 可复现性：**部分可复现**。`lock table : range → lock state` 与 scope expression 可零改动折算（等于 RdmaRangeLock 已有的 range 锁）；但 TrueTime / commit-wait / lock-free RO / wound-wait 在「单版本严格 2PL」下要么无意义（无版本即无快照读）、要么需引入版本层。判定：**范围锁数据结构可复现，非阻塞只读不可复现**。
- 关键原文证据：PAGE 3："At every replica that is a leader, each spanserver implements a **lock table** to implement concurrency control. The lock table contains the state for two-phase locking: **it maps ranges of keys to lock states**."；PAGE 8："**Reads within read-write transactions use wound-wait [33] to avoid deadlocks.**"；PAGE 6："Reads in a read-only transaction execute at a system-chosen timestamp **without locking, so that incoming writes are not blocked**."；PAGE 9："Such false conflicts can be removed by augmenting t_TM_safe with a **fine-grained mapping from key ranges to prepared-transaction timestamps**. This information can be stored in the lock table."

### 10 Making Snapshot Isolation Serializable（2005, ACM TODS 30(2), Fekete, Liarokapis, O'Neil, O'Neil, Shasha）

- 一句话问题：能否在不改 DBMS 引擎的前提下，用静态分析判定「一组事务程序在 SI 下是否永远可串行化」，并给出改程序的方法？
- 保护对象 / 粒度：**谓词读（predicate read `PR_i(P)`，返回满足条件的 item 集合）** + item 读/写；粒度可任意（TPC-C 分析用**字段级**）。保护对象是「读集 / 谓词读空间」，不是物理区间。
- 冲突/异常判定：**Theorem 2.1（危险结构定理，PAGE 15）**——任何非可串行化的 SI 历史，`DSG(H)` 的每个环中必存在三个连续事务 `Ti.1, Ti.2, Ti.3`（Ti.1 与 Ti.3 可相同），使 `Ti.1 → Ti.2` 与 `Ti.2 → Ti.3` 都是**并发事务间的 rw 反依赖（anti-dependency）**；结合 Lemma 2.3（并发事务之间的依赖必为 rw）与 Corollary 2.4（环上其余事务都运行在 Ti.2 的生命周期内）。静态版本：**Definition 3.5 Dangerous Structure（PAGE 23）**——`SDG(A)` 中存在节点 P、Q、R，使 `R ⇒ P`、`P ⇒ Q` 均为 vulnerable anti-dependency，且 `Q = R` 或 Q 可达 R（P 即 pivot）。**Theorem 3.1（PAGE 23–24）**：`SDG(A)` 无 dangerous structure ⇒ 应用在 SI 下所有执行可串行化；**Corollary 3.2**（每个顶点不同时有 vulnerable 入边和出边）。依赖定义见 Definition 2.1（PAGE 12）：wr / ww / rw（item 与 predicate 两版，含 `pr-rw` predicate anti-dependency）。
- 关键机制：①**DSG(H)**（多版本依赖序列化图，Definition 2.2，PAGE 13）与 **SDG(A)**（静态依赖图，Definition 3.3，PAGE 21），vulnerable 边记 `P ⇒ Q`。②**lifting**：把 DSG 的环提升到 SDG 的 circuit（PAGE 22），证明定理；注意「sinking」不总成立。③应用侧修复（不改引擎）：**Materialize the Conflict（PAGE 34）**——建 `Conflict(Id, val)` 表，对每条 vulnerable 边让两个程序都执行 `UPDATE Conflict SET val = val+1 WHERE Id = X`，借 First Committer Wins 制造 ww 冲突；对谓词冲突尤其有效（两程序可能本无公共数据项），可按参数（如 `TotalHours(eid, day, total)`）分桶避免全局串行。**Promotion（PAGE 35）**——把读提升为 identity write `SET X.c = X.c`（Oracle 下等价 `SELECT FOR UPDATE`），只改一个程序。④TPC-C 案例：按 if-then-else **splitting** 程序（DLVY→DLVY1/DLVY2，PAGE 28/31），证明 SDG(TPC-C) 无 dangerous structure（PAGE 32）；若不 split 会误判出危险结构。
- 正确性：给出的是**充分非必要条件**——PAGE 24 明说「the absence of dangerous structures ... is only a sufficient condition」，存在 dangerous structure 不等于一定有环，故**静态分析会产生假阳性**（可通过 splitting 缓解）。依赖前提：能静态获得全部程序逻辑与表/列访问、事务程序无任意运行时分支不可知、SI（First Committer Wins / First Updater Wins）。防写偏斜（Example 1.2, PAGE 6）、只读事务异常（Example 1.3, PAGE 7）、**predicate-based write skew**（Example 1.4, PAGE 9：两个并发 insert 都基于空谓词读，破坏「每人每天 ≤ 8 小时」约束）。
- 代价：无运行时内存/中止开销（纯静态分析）；修复后中止率上升（PAGE 36 实测 promotion 使 CPU +20%（低竞争）到 +35%（高竞争），abort 增加是主要信号）；**不需要全局时钟或中心节点**（离线分析）。
- 与 RdmaRangeLock 的关系：这是**整个 SSI 谱系的理论源头**（12 年后被 33 的 README 直接引为 [2]）。它不提供运行时机制，但给出「**两条相邻 rw 反依赖 = 危险结构**」这一判定规则，正是任何「非阻塞读范围标记」要检测的目标。对 RdmaRangeLock 的价值是：**可以用它作为对照实验的「正确性 oracle」**——构造写偏斜/predicate-based write skew 的 history，检查 `detect_conflict()` 是否等价于检出危险结构。完全不需要引入版本/时间戳即可在**验证脚本层**复现。
- 可复现性：**理论层完全可复现、运行层不适用**。最小改动：不改 `lock()` 语义，另写一个 `check_history()` 工具，把事务读/写记录成 item/predicate 依赖，构造 `DSG` 并用 Theorem 2.1 / Definition 3.5 判定；对 v1–v6 的每种范围粒度，统计「被判为危险结构但严格 2PL 本不会阻塞」的假阳性数。这是零前提改动的对照。
- 关键原文证据：PAGE 15（Theorem 2.1）："in every cycle there are three consecutive transactions Ti.1, Ti.2, Ti.3 ... such that Ti.1 and Ti.2 are concurrent, with an edge Ti.1 → Ti.2, and Ti.2 and Ti.3 are concurrent with an edge Ti.2 → Ti.3."；PAGE 23（Definition 3.5）："the static dependency graph SDG(A) has a **dangerous structure** if it contains nodes P, Q and R ... ### 30 Fast Serializable MVCC for Main-Memory Databases / HyPer（2015, SIGMOD '15, Neumann, Mühlbauer, Kemper）

- 一句话问题：能否让 MVCC 在保证**完全可串行化**的同时，几乎不比单版本串行执行慢，且不跟踪（可能巨大的）整个读集？
- 保护对象 / 粒度：**读谓词空间（intensional read predicate space）**——按 relation 记录 point / range lookup 的**比较摘要**；粒度有两级 **SR-RL（记录级）** 与 **SR-AL（属性级）**。不跟踪读集、不给索引键加 SIREAD/时间戳标记。
- 冲突/异常判定：**Precision Locking [17] 的适配**——提交时验证「近期已提交事务的（extensional）写是否与本事务的（intensional）读谓词空间相交」（Abstract, PAGE 1）；相交即 abort（"a validation fails if such an extensional write intersects with the intensional reads of the transaction under validation"，PAGE 4）。**Theorem（PAGE 7）**：遵循协议的任何多版本调度 H 的已提交投影，与「按 commitTime-stamp 排序的串行单版本调度 H'」冲突等价。
- 关键机制：①**版本维护**：in-place 更新 + undo buffer 存 before-image delta，VersionVector 串成 newest→oldest 版本链（PAGE 2–3）；`startTime` / `transactionID` / `commitTime` 三个时间戳，commitTime 决定串行序（PAGE 3, 7）。②**ww 立即中止**（PAGE 4），**rw 留到提交时验证**。③**Predicate Logging（PAGE 5）**：按 relation 把谓词记入 predicate log；索引访问「logging the point and **range lookups** on the index」；index nested-loop join 把读到的值 **coarsen 成 ranges** 再存为谓词；用 64-bit 整数比较摘要（字符串 hash）压缩。④**Predicate Tree (PT)（PAGE 5）**：per-relation 有向树，节点为单属性谓词（如 `B = 15`），边为 AND，所有路径的 OR 定义谓词空间，相同谓词节点合并。⑤**验证（PAGE 4–5）**：只遍历 `recentlyCommitted` 链中「T 生命周期内（startTime..commitTime）提交」的 undo buffers；对每个新建版本检查是否满足 T 的任一选择谓词（→ phantom / abort），对删除检查是否属于读集，对修改**同时检查 before-image 与 after-image**；成功则写 redo-log 并把 transactionID 时间戳改成 commitTime。⑥**object-by-predicate 验证**消除了谓词锁固有的 satisfiability 不可判定问题（PAGE 4）。⑦索引不用谓词锁/时间戳标记：更新索引列 = 删除 + 重插，索引保留所有对活跃事务可见的记录引用（PAGE 5–6）。⑧VersionedPositions 摘要保扫描性能（PAGE 6）。
- 正确性：防幻读（新建版本满足读谓词即 abort）、防写偏斜（提交时验证读谓词空间）、**假阳性**：SR-RL 因「记录级」把未读属性的修改也算冲突而较多，SR-AL 记录被访问属性可跳过无关版本（PAGE 5, 11）；PAGE 11 明说「Serializability validation with SR-AL creates almost no false positive aborts」，剩余假阳性来自 min/max 聚合尚未记录。依赖前提：undo buffer 在事务生命周期内保留、单节点 commitTime 计数器、|R| ≥ |W| 的工作负载假设。
- 代价：内存 = 极小的 predicate log（PAGE 11：TPC-C top-customer 查询传统读集需 ≥ 3 KB，SR-AL < 100 bytes，**30× 更省**）+ undo buffers + VersionedPositions；中止率 = 验证失败（phantom/read invalidation）；往返 = 单节点，提交需短临界区；开销实测 predicate logging 仅 **5%（SR-RL）/ 7%（SR-AL）**，PT 构建 2–15 µs（PAGE 10–11）；**不需要全局时钟/中心节点，只需一个 commitTime 计数器**；2PL 对照在 TPC-C 上比其慢约 5×（PAGE 9）。
- 与 RdmaRangeLock 的关系：**本组「可读范围保护」最直接的对照组之一**——「index range lookups 记成谓词」「把值 coarsen 成 ranges 存进 predicate log」几乎就是 `lock(S, key_range)` 的非阻塞版本；且 PAGE 12 §5.2 明确点名批评 SSI/PostgreSQL「tracking every single read, similar to read-locks」太贵，提出「不跟踪依赖、只跟踪读谓词」。要折算需引入：**MVCC 版本链（undo buffer）+ 提交时验证 + 中止** 三层；单版本严格 2PL 下 undo buffer 不存在，故不直接兼容。
- 可复现性：**可做「近似对照」，但必须引入提交时验证层**。最小改动：保留单版本 B+树与接口；把 `lock(S, range)` 改为「登记 range 谓词到 per-txn predicate log」（不阻塞）；维护一个 `recently_committed` 写集；在 `unlock_all()` 之前插入 `validate()`：若 T 生命周期内任何已提交写落在其任一 range 谓词内则 `detect_conflict() = true` 并中止 T。这就是「predicate log + commit-time validation」的最小内核；不需要版本、不需要时间戳（用本地单调计数器界定生命周期即可）。相比 07 的时间戳方案，它多一层「提交时验证」，少一层「时间排序」。
- 关键原文证据：PAGE 1（Abstract）："verifies that the **(extensional) writes of recently committed transactions do not intersect with the (intensional) read predicate space** of a committing transaction."；PAGE 5："Index accesses are treated similarly by **logging the point and range lookups on the index**." 与 "we subsequently **coarsen these values to ranges** and store these ranges as predicates in the predicate log instead."；PAGE 5："our MVCC implementation **does not use (predicate) locks and timestamps to mark read and modified keys in indexes**."；PAGE 4："For each newly created version, we check whether it satisfies any of T's selection predicates. If this is the case, T's read set is inconsistent because of the **detected phantom** and it has to be aborted."

### 32 Serializable Snapshot Isolation in PostgreSQL（2012, PVLDB 5(12), Ports & Grittner）

- 一句话问题：如何在一个**原本只有快照隔离、没有基于锁的可串行化级别**的生产数据库里，第一次把 SSI 落地，并控制内存与假阳性？
- 保护对象 / 粒度：**SIREAD 锁，多粒度 = relation / page / tuple；谓词读用 index-range locks（B+树 leaf page 上的「gaps」）**。B+树锁当前为 **page 粒度**，计划细化到 next-key locking（PAGE 7）。
- 冲突/异常判定：**Theorem 1（PAGE 4，Fekete et al. 的强化版）**："Every cycle in the serialization history graph contains a sequence of edges `T1 rw→ T2 rw→ T3` where each edge is a rw-antidependency. Furthermore, **T3 must be the first transaction in the cycle to commit**."；Corollary 2（T1 并发 T2、T2 并发 T3）。SSI 判定规则（PAGE 4）：检查「**dangerous structure** = 两条相邻 rw-antidependency」，**若任何事务同时有 incoming 与 outgoing rw-antidependency 就中止其中一个**；只跟踪 rw，不跟踪 wr/ww。额外 **Theorem 3（PAGE 5）**：若 T1 只读，则只有 `T3 在 T1 取快照前提交` 才可能异常 → read-only snapshot ordering rule。**safe snapshots**（PAGE 5）：无并发 RW 事务带 rw 出边到「早于本快照提交的事务」时，只读事务可完全免 SSI 开销；**deferrable transactions**（PAGE 6）等待 safe snapshot。
- 关键机制：①**冲突检测双路径（PAGE 7）**：写先于读 → 用 MVCC 的 `xmin/xmax` 可见性检查直接推断 rw-conflict，**无需锁**；读先于写 → 必须靠 **SIREAD 锁**，且要支持 predicate reads。②**SSI lock manager（PAGE 7）**：只存 SIREAD、不阻塞、无死锁检测；读在所有访问 tuple 上取锁，索引 AM 在 **gaps** 上取锁防幻读；heap/index 锁可**提升为更粗粒度**（多 tuple → 单 page）；**不需要 intention locks**（尽管用了多粒度锁），写 tuple 时按「coarsest to finest」逐粒度检查；DDL 改物理位置时 page/tuple 锁提升为 relation 级，索引被删时 gap 锁替换为 heap 的 relation 级锁。③**每事务保存所有 rw-antidependency 的 in/out 列表**（指针而非单 bit，PAGE 8），不存 wr/ww；用 PSSI 的 cycle-testing 被否决（内存 + 库外 wr 依赖无法跟踪）。④**safe retry（PAGE 8）**三条规则：T3 提交前不中止；尽量中止 pivot/T2；若 T2、T3 都已提交则中止 T1；2PC 下可能无法保证（PAGE 9，明确出现 "pivot"）。⑤**内存四技术（PAGE 8–9）**：safe snapshots/deferrable、granularity promotion、aggressive cleanup（保留「最早出边冲突的 commit sequence number」）、**summarization**（把多个已提交事务的 SIREAD 合并到一个 dummy transaction，配 commitSeqNo；映射表可换出到磁盘 LRU）。⑥特性集成：2PC 把 SIREAD 写盘（PAGE 9）、流复制只允许 safe snapshot 上的只读事务（PAGE 10）、savepoint/subtransaction 不丢 SIREAD（PAGE 10）、只有 B+-tree 支持 predicate locking（PAGE 10）。
- 正确性：防幻读（index gap 锁）、防写偏斜（dangerous structure）、**假阳性明确存在**（PAGE 4："not every dangerous structure is part of a cycle"；PAGE 5 举例：T1 只读且无 T3→T1 路径时仍会被中止）；PSSI 可降 40% 假中止但被否。依赖前提：全部事务都运行在 SERIALIZABLE 级（PAGE 4 README 亦强调）、SI/MVCC、能自动重试 40001。
- 代价：内存 = 固定大小共享内存锁表 + rw-conflict 图 + SLRU 换出；中止率 = serialization failure < 0.25%（DBT-2++）/ 0.03%（RUBiS，PAGE 11）；CPU 开销 SIBENCH 10–20%（PAGE 11）、DBT-2++ 5%（PAGE 11），论文摘要称相对 SI **< 7%**（PAGE 1）；**不需要全局时钟/中心节点**（单节点，用本地 commit sequence number）；S2PL 基线显著更慢（PAGE 10–11）。
- 与 RdmaRangeLock 的关系：**关键桥梁**。PAGE 3 明说 S2PL 防幻读「must be predicate locks, usually implemented using **index-range locks**」；PAGE 10 更给出决定性证据：**其 S2PL 对照实现「reuses our SSI lock manager's support for index-range and multigranularity locking; rather than acquiring SIREAD locks, it instead acquires 'classic' read locks」**——即同一套「index-range + 多粒度提升」的**范围标记数据结构**可以同时服务阻塞 2PL 与非阻塞 SIREAD。因此它是与 `lock(mode, key_range)` / `get_lock_count()` 同构性最强的一篇。但要引入 MVCC 版本（xmin/xmax）、SIREAD 生命周期延长到「所有并发事务结束」、提交时危险结构判定与中止。
- 可复现性：**范围标记结构可零改动折算，非阻塞语义需引入提交时验证**。最小改动：把 `lock(S, range)` 的锁对象定义为「B+树 leaf page + gap」（对应 `predicate` / `exact-range` 粒度），实现 33/34 的 tuple→page→relation 粒度提升并用 `get_lock_count()` 度量提升收益（这与现有指标天然吻合）；再把「读锁阻塞写」换成「登记 SIREAD 标记 + 写时检查 + 提交时按 dangerous structure 中止」。这一步就离开严格 2PL。
- 关键原文证据：PAGE 3："To prevent phantoms, these locks must be predicate locks, usually implemented using **index-range locks**."；PAGE 4："it checks for a '**dangerous structure**' of two adjacent rw-antidependency edges. If any transaction has both an incoming rw-antidependency and an outgoing one, SSI aborts one of the transactions involved."；PAGE 5："**SIREAD** ... These locks **do not block conflicting writes** (thus, 'lock' is somewhat of a misnomer)."；PAGE 7："index access methods acquire SIREAD locks on the '**gaps**' to detect phantoms. Currently, locks on B+-tree indexes are acquired at **page granularity** ... Both heap and index locks can be **promoted to coarser granularities** to save space"; PAGE 10："This implementation **reuses our SSI lock manager's support for index-range and multigranularity locking**; rather than acquiring SIREAD locks, it instead acquires 'classic' read locks."

- 一句话问题：把 PostgreSQL 9.1 的 SSI 实现中「约 90% 其实是 predicate locking」这一层的算法、粒度、索引 AM 规则与工程差异写成权威说明。

- 可复现性：**「范围标记 + 粒度提升」可零改动复现**；「非阻塞 + 提交时中止」需引入至少一层提交时验证。最小改动即：把 v1–v6 的锁表改成三级（tuple/page/relation），实现 33 的提升规则并统计 `get_lock_count()`；再把读锁从「阻塞」切到「SIREAD 标记 + 危险结构中止」，即可与阻塞版做 A/B 对照。

- 保护对象 / 粒度：**predicate lock，三级 `PREDLOCKTAG_RELATION / PAGE / TUPLE`（PAGE 8）**；tuple 读 → tuple 锁；**无匹配键值时：seq scan 取 relation 级锁，index scan 取覆盖 search key 的 page 级锁（无论当前是否有匹配键）**——这是「可读范围保护」落到代码的一句话规格（PAGE 1）。
- 冲突/异常判定：由 `CheckForSerializableConflictOut/In`（PAGE 4 的 predicate.h 声明）与 `PreCommit_CheckForSerializationFailure` 完成；提交信息（PAGE 1）描述为「a predicate lock manager observes the reads and writes performed and **aborts transactions if it detects that an anomaly might occur**」，并承认「produces some false positives」。理论判定同 33 的 dangerous structure。
- 关键机制：①**`SERIALIZABLEXACT`（PAGE 5）**：`outConflicts` / `inConflicts` / `predicateLocks` / `possibleUnsafeConflicts` 四个 SHM_QUEUE、`commitSeqNo`、`earliestOutConflictCommit`、`finishedBefore`、`xmin`，flags 含 `SXACT_FLAG_ROLLED_BACK / COMMITTED / CONFLICT_OUT / READ_ONLY / DID_WRITE / DEFERRABLE_WAITING / RO_SAFE / SUMMARY_CONFLICT_IN / SUMMARY_CONFLICT_OUT / PREPARED`。②**`RWConflictData`（PAGE 6）** 记录 in/out 冲突对；`SerCommitSeqNo`（PAGE 5）含 Invalid/Recovery/FirstNormal 保留值。③**`PREDICATELOCKTARGETTAG`（PAGE 7）** 16 字节 5 字段，宏区分 RELATION/PAGE/TUPLE；`PREDICATELOCKTARGET` 带 `priorVersionOfRow` / `nextVersionOfRow`；`LOCALPREDICATELOCK`（PAGE 8）进程本地 `held` + `childLocks` 用于提升决策。④**`PredicateLockPageSplit / PageCombine`**（PAGE 4）保证页分裂/合并时谓词锁不丢。⑤**两级提升（PAGE 1）**：同页 tuple 锁过多 → page 锁 → 必要时 relation 锁。⑥**生命周期（PAGE 1）**："Predicate locks can't be released at commit, but must be remembered until all the transactions that overlapped with it have completed"，故用 lossy conservative 摘要 + **`pg_serial` SLRU pool** 溢出。⑦**2PC 支持**（PAGE 3 的 `TWOPHASE_RM_PREDICATELOCK_ID`、PAGE 9 的 `TwoPhasePredicateXactRecord/LockRecord`），恢复后保守假定 prepared 事务「both in and out conflicts」。⑧`pg_am` 新增 **`ampredlocks`** 列，仅 btree 置 t（PAGE 2–3）。⑨Hot Standby 暂不允许 SERIALIZABLE（PAGE 1）。
- 正确性：防幻读（无匹配键的 index scan 也取 page 锁）、防写偏斜；**假阳性**来自 lossy 摘要、粗粒度提升、以及 2PC 恢复后的保守 in/out 假设。依赖前提：MVCC、全部事务 SERIALIZABLE、SIREAD 跨事务存活。
- 代价：内存 = `max_predicate_locks_per_xact` 固定共享内存 + SLRU（有上界）；中止率 = 40001；往返 = 单节点提交前检查；**不需要全局时钟/中心节点**（`LastSxactCommitSeqNo` 是本地严格单调计数器）。
- 与 RdmaRangeLock 的关系：把 33 的设计落成**可直接照抄的数据结构清单**（三级 tag、提升计数、页分裂复制、SLRU）。`index scan 对无匹配 key 取 page 级锁` 与 RdmaRangeLock 新增的 `predicate` / `exact-range` 是同一问题（保护「当前为空但可能被插入」的范围）。需要引入：MVCC、SIREAD 跨提交存活、提交时中止。
- 可复现性：**「三级粒度 + 提升 + 页分裂复制」可零改动复现**；非阻塞语义需引入提交时验证。最小改动：把 v1–v6 的锁对象换成 `(relation, page, tuple)` 三级 tag，实现 `childLocks` 计数触发提升，让 `get_lock_count()` 直接量化提升收益；这是最贴近现有接口的一个对照实验。
- 关键原文证据：PAGE 1："Whenever a tuple is read, a predicate lock is acquired on the tuple. Shared memory is finite, so when a transaction takes many tuple-level locks on a page, the locks are **promoted to a single page-level lock, and further to a single relation level lock** if necessary. **To lock key values with no matching tuple, a sequential scan always takes a relation-level lock, and an index scan acquires a page-level lock that covers the search key, whether or not there are any matching keys at the moment.**"；PAGE 1："A predicate lock **doesn't conflict with any regular locks** or with another predicate locks in the normal sense. They're only used by the predicate lock manager to detect the danger of anomalies."；PAGE 1："Predicate locks **can't be released at commit, but must be remembered until all the transactions that overlapped with it have completed**."

### 37 Silo: Speedy Transactions in Multicore In-Memory Databases（2013, SOSP '13, Tu, Zheng, Kohler, Liskov, Madden）

- 一句话问题：能否设计一种 OCC 提交协议，使**只读记录完全不写共享内存**（无读锁、无集中 TID 分配），却仍保证可串行化且崩溃后可恢复？
- 保护对象 / 粒度：**read set R（记录 + 读时 TID）+ write set W + node set N（扫描覆盖的 B+树叶节点 + 其版本号）**。范围查询的保护粒度是**叶节点版本**而非每个 key。
- 冲突/异常判定：**提交时版本校验**（Figure 2, PAGE 6）：Phase 2 对 `R` 中每条记录验证 `tid == read-tid && latest && !(locked && not in W)`，对 `N` 中每节点验证 `node.version == version`，任一不符即 abort。正确性论证用**归约到 S2PL**（PAGE 6："We argue its serializability by reduction to strict two-phase locking (S2PL): if our OCC validation protocol commits, then so would S2PL."）；epoch 边界服从 dependencies 与 anti-dependencies。
- 关键机制：①**Epochs（PAGE 4–5）**：全局 `E` 由指定线程每 40 ms 推进（无锁），每 worker 本地 `e_w` 且 `E − e_w ≤ 1`；读取 `E` 的时刻是 **serialization point**（PAGE 6）。②**TID（PAGE 4–5）**：64 位 = epoch 高位 + 同 epoch 内序号 + 低 3 位状态位（lock / latest-version / absent）；**分散分配**，worker 只在验证可提交后取「大于所有读/写记录 TID、大于本 worker 最近 TID、且在当前 epoch」的最小数；明说 **TID 不反映 anti-dependencies（write-after-read）**（PAGE 5）。③**三阶段提交（PAGE 5–6）**：Phase 1 按全局序（记录指针地址）锁 W 全部记录 → fence → `e ← E` → fence；Phase 2 验证 R 与 N、`generate-tid(R,W,e)`；Phase 3 写 W 并解锁（TID 与 lock 同字，原子释放）。④**§4.6 Range queries and phantoms（PAGE 7）**：明确拒绝 next-key locking（"requires locking for reads, which goes against Silo's design philosophy"），改用 B+树**每个叶节点的 version number**：扫描 `[a,b)` 时把区间内记录加入 `R`，同时把「与 `[a,b)` 重叠的叶节点 + 扫描时读到的 version」加入 **node-set**；Phase 2 校验所有 node version 未变，从而保证「没有新键加入/移出被查范围」。查找/删除因键不存在而失败时也把「将包含该缺失键的节点」加入 node-set（提交条件是键仍不在树中）。⑤insert 引起结构修改的区分（PAGE 7–8）：对受影响的节点 n，`v_old → v_new`，若 n 在 node-set 中且记为 `v_old` 就改成 `v_new`，否则 abort——只有其他并发修改才导致中止。⑥insert 用 `insert-if-absent` 先放 absent 占位记录（TID 0）并同时加入 R/W（PAGE 7）。⑦**snapshot transactions**（PAGE 8）：只读事务在 snapshot epoch（`k=25`，约每秒一次）的一致快照上跑，**永不 abort**；靠 previous-version 指针保留版本。⑧epoch-based RCU 垃圾回收（PAGE 8）、整 epoch group commit 的 durability（PAGE 8–9）。
- 正确性：防幻读（node-set version 校验）、防写偏斜（OCC 读集校验，归约到 S2PL）、**假阳性**：任何对叶节点的结构修改（split等）都会改 version 从而误伤不相关范围查询；论文未量化。依赖前提：one-shot 请求模型、短事务、in-place 更新 + version validation 双重读校验、无集中点。
- 代价：内存 = R/W/N 三个 thread-local 集合 + 记录 TID 字 + 快照版本链（实测快照空间开销仅 3.4%，PAGE 13）；中止率 = 验证失败（长只读事务用快照规避，PAGE 13 实测 abort 从 15,756/s 降到 2,570/s）；往返 = 单节点无网络（PAGE 2、10）；**不需要全局时钟/中心节点**（明确消除 centralized TID 与 lock manager；只有 40 ms 的全局 epoch 计数器，且无锁）；持久化按 epoch 批量，提交延迟受 epoch 周期影响。
- 与 RdmaRangeLock 的关系：**本组唯一「不引入版本/时间戳、只用 B+树节点版本号」就能防幻读的方案**，且底层就是 B+树（Masstree），与 RdmaRangeLock 的索引主线天然一致。node-set = 「把可读范围折算成被扫描叶节点集合」，是 `get_lock_count()` 最省内存的对照（锁数 ≈ 叶节点数而非 key 数）。明确点名 next-key locking 因需要读锁而违背设计哲学，正好回答「不用阻塞锁防幻读」。需要引入：**提交时验证 + 中止**、每叶节点一个 version、事务可重启；仍需 epoch 计数器（但不是全局时钟）。
- 可复现性：**本组最接近「可复现近似对照」的一篇**。最小改动（不引入 MVCC、不引入时间戳排序）：在 B+树每个叶节点加 `version`，`lock(S, range)` 时不下读锁，而是把「覆盖该 range 的叶节点 id + 当前 version」记进事务本地 `node_set`；任何 `lock(X, key)` 引起的插入/删除/分裂对相关叶节点 `version += 1`；`unlock_all()` 前做一次 `validate()`：若 node_set 中任一 version 变化则 `detect_conflict() = true` 并中止该事务。`get_lock_count()` 改为统计 node_set 条目数，可直接与 v1–v6 的锁数对比。这是「非阻塞读范围标记」在单版本 B+树上**改动最小**的实现，代价是引入「提交时验证 + 中止」（因此不再是严格 2PL）。
- 关键原文证据：PAGE 7："The typical solution to this problem in database systems is **next-key locking [24]. Next-key locking, however, requires locking for reads, which goes against Silo's design philosophy.**"；PAGE 7："Silo deals with this issue by taking advantage of the underlying **B+-tree's version number on each leaf node** ... we also maintain an additional set, called the **node-set**. We add the leaf nodes that overlap with the key space [a, b) to the node-set along with the version numbers examined during the scan. **Phase 2 checks that the version numbers of all tree nodes in the node-set have not changed, which ensures that no new keys have been added or removed within the ranges examined.**"；PAGE 6（Figure 2）："Data: **read set R, write set W, node set N**, global epoch number E" 及 "for node, version in N do if node.version ≠ version then abort();"；PAGE 6："if our OCC validation protocol commits, then so would S2PL."

### 39 TicToc: Time Traveling Optimistic Concurrency Control（2016, SIGMOD '16, Yu, Pavlo, Sanchez, Devadas）

- 一句话问题：能否不给事务分配时间戳，改由数据项携带 wts/rts、在提交时惰性计算合法 commit_ts，从而消除集中式时间戳分配瓶颈并减少不必要的中止？
- 保护对象 / 粒度：**每个 tuple 的「有效时间戳区间 [wts, rts]」**（read set / write set 各存 `{tuple, data, wts, rts}`）；粒度是**单元组**，**没有范围/谓词保护**（见下）。
- 冲突/异常判定：**提交不变量式 (1)（PAGE 3）**：`∃ commit_ts, (∀v ∈ 读版本, v.wts ≤ commit_ts ≤ v.rts) ∧ (∀v ∈ 写版本, v.rts < commit_ts)`；**Definition 1 Serial Order（PAGE 6）**：`A <_s B ≜ A <_ts B ∨ (A =_ts B ∧ A ≤_pt B)`；**Theorem 1**："Any schedule in TicToc is equivalent to the serial schedule defined in Definition 1"，由 Lemma 1（写同 tuple 者 commit_ts 必不同）、Lemma 2（同 ts 且同物理时刻者不冲突）、Lemma 3（读返回串行序里的最新写）证明。
- 关键机制：①**data-driven timestamp management**（PAGE 1, 3）：wts = 版本创建时间戳，rts = 版本有效至；逻辑时间戳与物理时间解耦，可「时间旅行」把 `rts` 向后延展（`r.tuple.rts = max(commit_ts, rts)`，Algorithm 2 行 17）。②**OCC 三阶段**：Read Phase（Algorithm 1，PAGE 3）原子加载 `value/wts/rts` 到私有 workspace；Validation Phase（Algorithm 2，PAGE 4）Step 1 按主键序锁 W（防死锁）→ Step 2 `commit_ts = max(WS 的 rts+1, RS 的 wts)` → Step 3 验证 RS：若 `r.rts < commit_ts` 且 wts 已变或被他人锁则 abort，否则延展 rts；Write Phase（Algorithm 3，PAGE 4）设 `wts = rts = commit_ts` 并解锁。③**TS_word（PAGE 5）**：64 位 = 1 bit lock + 15 bit `delta = rts − wts` + 48 bit wts，用 Silo 式双读校验（Algorithm 4/5）无锁原子读；CAS 延展 rts。④**优化（PAGE 7–8）**：no-wait locking（抢锁失败立即 abort 重试，源自 2PL non-waiting deadlock prevention）、preemptive aborts（用近似 commit_ts 提前中止）、timestamp history（per-tuple wts 历史，比 MVCC 省，因为不存值）、SI/RR 低隔离级别（两个 commit 时间戳 `commit_rts`/`commit_wts`）。⑤**明确不解决幻读**（PAGE 5 §3.6 末尾，见下引文）——把「把 data-driven timestamp 用到 order-preserving indexes 以避 phantom」留作 future work。
- 正确性：防写偏斜 / 保证可串行化（Theorem 1，配合 no-wait 等）；**不防幻读**（作者自认，PAGE 5）；**假阳性 = spurious aborts（PAGE 5 §3.4）**：因依赖环 A<B<C 而中止，"A aborts not because of the timestamps and not data values"，且只有并发事务能导致中止。依赖前提：tuple 可原子读写 TS_word、事务可重启、one-shot 类请求；**not order-preserving serializable**（PAGE 5，逻辑序可能与提交序不一致）。
- 代价：内存 = 每 tuple 一个 64-bit TS_word + 可选的 wts history（PAGE 8，比 MVCC 小，不存旧值）；中止率 = 比其他 OCC 低（最多 3.3×，PAGE 1 / PAGE 12）；吞吐最高 +92%（PAGE 1）；往返 = 单节点；**不需要全局时钟/中心节点**（核心贡献就是消除 centralized timestamp allocation，PAGE 1；对照 HEKATON 被单全局原子计数器限在 ~5M ts/s，PAGE 10）。
- 与 RdmaRangeLock 的关系：**关系最弱的一篇**。它是纯元组级 OCC，作者自己承认「扫描会漏掉并发插入的 tuple」，标准解法（index locks / validation rescan）都被认为太贵而放弃，且明确把「保序索引上的 anti-phantom」列为未来工作。因此它**不能**作为「可读范围保护」的对照实现，只能作为「无范围保护时会出什么问题」的反例、以及「时间戳区间可压缩标记」的思路来源（wts/rts 区间与 07 的 timestamp cache / 09 的 key-range→timestamp 同属「用时间区间描述数据有效性」）。
- 可复现性：**就「范围查询锁」主题判定为不可复现**（原文自认未实现 phantom 防护）。若只做「元组级 OCC 对照」可复现（元组加 wts/rts + 提交时验证），但与 `lock(mode, key_range)` 的范围语义不匹配；除非额外实现作者留作 future work 的「保序索引 data-driven timestamp」，那已超出本组范围。
- 关键原文证据：PAGE 1（Abstract）："this protocol **assigns read and write timestamps to data items** and uses them to **lazily compute a valid commit timestamp** for each transaction. TicToc removes the need for centralized timestamp allocation"；PAGE 3（式 1）："`∃ commit_ts, (∀v∈{versions read by T}, v.wts ≤ commit_ts ≤ v.rts) ∧ (∀v∈{versions written by T}, v.rts < commit_ts)`"；PAGE 5（§3.6）："**Scanning tuples in a database may miss tuples being inserted** because they are not observed by the scanning transaction. Standard techniques for solving this problem include using locks in indexes [31] or rescanning the tuples during the validation phase [24]. Both techniques incur significant performance overhead. ... **We believe that it is possible to apply the data-driven timestamp management concept used in TicToc to order-preserving indexes to avoid this phantom anomaly** for serializable transactions. **This exploration is outside of the scope of this paper and is left for future work.**"

**因果链一句话**：SI 写偏斜（1995）→ Adya 依赖图（1999/2000）→ 只读异常（2004）→ **Fekete 危险结构定理（2005，静态）** → **Cahill SSI（2008，运行时 + SIREAD）** → PSSI 精度上界（2011）→ **PostgreSQL 9.1 首个生产实现（2011 commit / 2012 论文与 README）** → 分布式侧由 **Spanner TrueTime（2012）** 与 **CockroachDB timestamp cache（2016）** 把「读范围」折算成「key range → 时间戳/锁状态」；旁路 **Silo（2013，节点版本）**、**HyPer（2015，谓词日志）** 提供了不依赖 SIREAD 的两种轻量替代，而 **TicToc（2016）** 明确把范围保护留白。

## 对照结论

### (a) 有没有一种方案可以在「不改单版本 + 严格 2PL」前提下，作为「非阻塞读范围标记」实现成可对比版本？

**严格按字面回答：没有，10 篇里一篇都没有。** 理由来自三处原文，互相印证：

1. 「非阻塞读范围标记」的本质是**把冲突判定从「读的当时」推迟到「写之后 / 提交时」**，而单版本 + 严格 2PL 只能把判定放在「读的当时」——因为读锁一旦不阻塞写，写就会**原地覆盖**唯一版本，事后既拿不回旧值（无 MVCC）、又没有时间戳可供比较（无时间层）、更没有「验证并中止」的窗口（严格 2PL 无提交时验证）。32 PAGE 3 把这一点说得很清楚：S2PL 要防幻读「**must be predicate locks, usually implemented using index-range locks**」——即阻塞式范围锁，而不是非阻塞标记。
2. 本组所有「非阻塞」方案都至少引入了一层新机制：MVCC 版本（09/30/32/33/34）、读时间戳或时间区间（07/08/39）、提交时验证 + 中止（30/32/33/34/37/39）、节点版本号（37）。07 PAGE 3 甚至把「Lockless」直接定义为「**Correctness is enforced by aborting transactions**」——中止是必要组件，而严格 2PL 用阻塞代替中止。
3. 39 PAGE 5 的反例最直白：连 TicToc 这种纯 OCC 都承认「扫描会漏掉并发插入」，标准解法（index locks / validation rescan）都被判太贵，只能把保序索引上的防幻读留作 future work。也就是说，**一旦抽掉「版本 / 时间戳 / 提交时验证」这三层中的全部，连范围保护都做不到**。

**但有一个必须区分清楚的「半个答案」**：如果把问题里的「非阻塞」放宽为「范围标记的数据结构」，那么 **09（Spanner 的 `lock table: ranges of keys → lock states`、PAGE 9 的 key ranges → timestamps）**、**32/33/34（PostgreSQL 的 index-range + gap 锁 + tuple→page→relation 多粒度提升）** 这三篇是**可以零改动折算回 RdmaRangeLock** 的——因为它们本来就是**阻塞式范围锁**，与 `lock(mode, key_range)` / `get_lock_count()` 同构。最强证据是 32 PAGE 10：其 S2PL 基线「**reuses our SSI lock manager's support for index-range and multigranularity locking; rather than acquiring SIREAD locks, it instead acquires 'classic' read locks**」——同一套范围标记结构同时服务阻塞 2PL 与非阻塞 SSI。33 PAGE 5 也说「**Both S2PL and SSI require some form of predicate locking**」。

因此准确表述是：**「可读范围」这一粒度维度可以 100% 复用（正好对应 v1–v6 / predicate / exact-range）；「非阻塞」这一语义维度在单版本严格 2PL 下无法复用。** 报告里应把这两篇作为「**粒度/谓词范围**」对照基线，而非「非阻塞」对照基线，并注明 33 PAGE 5 的「粗粒度导致假阳性、数量受 plan choice 影响」是两者共享的权衡轴。

### (b) 如果不能，最少需要引入哪一层（版本、时间戳、提交时验证）？给出可落地的实验设计要点

**最少只需引入一层：「提交时验证 + 中止/重试」，配合一个「记录读过哪些范围」的标记结构。不需要 MVCC 版本、不需要全局时钟、不需要中心节点。**

依据：
- **07 PAGE 7–8** 的 timestamp cache 与 **32/33/34** 的 SIREAD，其极简内核都是「读时在范围上留一个不阻塞的标记 → 写时查标记 → 冲突则中止」；这一步根本用不到多版本（多版本只是为了让「读」能继续看到旧值，属于**优化并发度**而非**保证正确性**所必需）。
- 但要同时防**写偏斜**（不只防幻读），单靠「写检查读标记」不够（单条 rw 反依赖无害），必须再检测 **dangerous structure `Tin → Tpivot → Tout`**（33 PAGE 3 / 10 Definition 3.5 / 32 PAGE 4 Theorem 1），也就是每事务维护 `conflictIn`/`conflictOut` 列表并在提交时判定、按 **safe retry**（32 PAGE 8）选中止对象。这就是那一层「提交时验证」的全部内容。
- **37 PAGE 7** 的 node-set 进一步说明：连「时间戳」都可以不要——只要每个 B+树叶节点有一个 `version`，提交时验证 version 未变即可。这是三个候选里**最省、最贴合单版本 B+树**的一层。
- 反过来，若目标是「写不被阻塞、且读事务也不被中止」（真正的无阻塞通过），才必须再引入 **版本层**（让写不覆盖旧值）或 **时间戳区间层**（07/08 HLC、09 TrueTime、39 wts/rts）；那一步才真正破坏「单版本」前提，应单独标注。

**可落地实验设计（对照版本建议命名 `v-ssiread` / `v-nodeset`，与 v1–v6 并列）**

1. **接口与基线不动**：保留 `lock(mode, key_range)` / `unlock_all()` / `get_lock_count()` / `detect_conflict()`，单版本 B+树，写锁仍严格 2PL 持有到 `unlock_all()`。基线 = v6 阻塞式范围锁。
2. **把读锁换成非阻塞范围标记**（三选一，正对应本组三种机制）：
   - **A｜SIREAD 标记**（照 32/33/34）：`lock(S, range)` 只登记 `(range, txn)`，不阻塞写；锁对象按 B+树 leaf page + gap 对齐（33 PAGE 6「lock the gaps between and surrounding index entries within the scanned range」），实现 **tuple→page→relation 提升**（34 PAGE 1 / 33 PAGE 5：取粗锁自动释放其覆盖的细锁）。**`get_lock_count()` 直接复用为提升收益指标**——这是与现有实现最自然的一个对照。
   - **B｜timestamp cache 标记**（照 07/08）：`range → high-water read_ts`；`lock(X, key)` 时若 `write_ts < cache_ts` 则 `detect_conflict() = true` 并中止写者。需要引入**一个本地单调计数器**当事务时间戳（不要 HLC/全局时钟）。
   - **C｜node-set 标记**（照 37，最省）：每个叶节点加 `version`；`lock(S, range)` 记 `(leaf_id, version)` 到事务本地 node_set；插入/删除/分裂对相关叶节点 `version += 1`；`get_lock_count()` 统计 node_set 条目数。**无版本链、无时间戳、无中心节点**，是本组最接近「最小改动」的方案。
3. **写路径**：`lock(X, key)` 时检查 key 是否落在任一活跃标记范围内（A/C 用区间包含，B 用时间戳比较），命中即记录一条 rw-antidependency `reader → writer`（32 PAGE 7 的「读先于写」分支；单版本下不需要 MVCC 的 xmin/xmax 来判「写先于读」，因为写侧检查已覆盖）。
4. **提交时验证（那一层最小新增）**：每事务维护 `conflictIn` / `conflictOut` 列表（32 PAGE 8 / 33 PAGE 9 的 rw-conflicts 列表，明确优于单 bit 指针）；在 `unlock_all()` 之前检测 `Tin → Tpivot → Tout` 危险结构（33 PAGE 3），并按 **safe retry** 三条规则（32 PAGE 8：T3 提交前不中止、优先中止 pivot/T2、否则中止 T1）选中止对象；照 33 PAGE 3 的 `Tout 必须先提交` 与 **Theorem 3 只读优化**降低假阳性。
5. **标记生命周期**：标记**不能**在 `unlock_all()` 时清除，必须保留到「所有与该事务重叠的并发事务结束」（32 PAGE 5 / 34 PAGE 1）；用「最老活跃事务」水位做清理（33 PAGE 8 的 `SerializableGlobalXmin` 思路），内存超限时把多个已提交事务的标记合并到 dummy txn（32 PAGE 9 summarization）。
6. **度量与对照矩阵**（这是综述最需要的数据）：
   - 横轴 = 范围粒度：`exact-range` / `predicate` / leaf-page / relation（对应 v1–v6 的粒度层级 + 33 的三级）。
   - 纵轴 = 三个指标：`get_lock_count()`（内存/锁数）、abort rate（含**假阳性**）、吞吐/阻塞等待时间。
   - 预期结论（有原文支撑）：粒度越粗 → 锁数越少但假阳性越高（33 PAGE 5「Coarse granularities can cause some false positive indications of conflict. The number of false positives can be influenced by plan choice.」；10 PAGE 24「absence of dangerous structures ... only a sufficient condition」；30 PAGE 11 SR-RL 比 SR-AL 假阳性多）；dangerous structure 是充分非必要判定，故 `v-ssiread` 的 abort 必然 ≥ v6 的阻塞次数。
   - 若要做「正确性 oracle」，用 **10 的 Theorem 2.1 / Definition 3.5** 写一个 `check_history()`，对写偏斜、Example 1.4 predicate-based write skew、只读事务异常三类 history 验证 v6 与各对照版是否等价——**这一项零前提改动**。
7. **明确判定为不可复现 / 需额外前提的部分**（在报告中单独标注，避免污染分类纯度）：
   - **09 TrueTime / commit-wait**：需 GPS/原子钟硬件与 ϵ 界，单版本下无意义 → 不可复现。
   - **08 read refreshing / HLC / Follower Reads / closed timestamps**：需版本链与时钟同步 → 不可复现。
   - **30 HyPer / 32–34 SSI 完整形态**：需 MVCC 多版本存储（undo buffer / xmin-xmax）→ 单版本下只能做上述「近似对照」。
   - **39 TicToc**：作者自认未实现幻读防护（PAGE 5）→ **就本主题判定为不可复现**，仅作反例。
   - **07/08 的 push / priority / wound-wait（09）**：属「谁被中止」的策略层，可选用，不影响核心结论。

**给报告的一句话结论**：本组 10 篇里，**没有任何一篇**能在「单版本 + 严格 2PL」不变的前提下实现「非阻塞读范围标记」；最少要加的是**「提交时验证 + 中止」一层**，而**「可读范围」的粒度、gap 锁、三级提升、`get_lock_count()` 度量**可以从 32/33/34（以及 09 的 range→lock-state）**零改动借用**。三个可落地近似版中，**37 的 node-set（B+树叶节点 version）改动最小、且不需要版本也不需要时间戳**，最适合作为 v1–v6 之外的第一个对照实验；**07 的 interval timestamp cache** 次之（只需一个本地计数器）；**30 的 predicate log** 再次（需提交时验证 + 最近写集）。所有近似版都必须在报告中标注：它们已因「读不阻塞写 + 提交时中止」而离开纯封锁分类，只是对照组，不并入 RdmaRangeLock 的 v1–v6 主线。
