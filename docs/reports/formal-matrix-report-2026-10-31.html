01一句话结论

这一轮 756 个 case 全部跑完、零失败，但它测到的不是并发度，而是互斥锁排队。 所有锁协议（以及无锁基线）都随线程数单调下降；唯一干净的对比维度是单线程开销， 以及不同协议在同一范围下付出的锁数量差异。

  • 能用的：单线程吞吐（图 7）、锁数量与每行锁成本（图 5）、bucket 宽度与负载的交互（图 6）。
  • 不能用的：任何"t32 比 t4 快"或"某协议扩展性更好"的说法——全体曲线都在下降，排序只反映谁更早撞上全局互斥锁。
  • 没测到的：幻读防护。YCSB-E 的插入不落在扫描区间内，v3/v4/v5 的中止率全程为 0。

04发现的问题

A–F 是从这一轮数据里读出来的；G 是执行过程中暴露的脚本缺陷。

Abucket 宽度的最优值随负载反转，固定值无法两用

fig05；`include/lock/remote_lock_manager.h` / `src/txn/workload.cpp`

证据　YCSB-E 上 256 > 64 > 16，YCSB-A 上 16 > 64 > 256，两条曲线完全反序。矩阵固定 bucket=64，两类负载都不占优。

影响　v6 的结论不能写成「层级锁更好」，必须绑定 bucket 宽度与负载类型；把 bucket 做成按 workload 可配，并把 16/64/256 三条完整曲线都跑出来。

BYCSB-E 的插入永远落在扫描区间之外，幻读防护未被测量

`src/txn/workload.cpp` 中的 `ycsb()`

证据　插入 key = `key_count + n*ops + i`（恒 ≥ key_count），范围读上界 ≤ key_count，两者系统性不相交。实测 YCSB-E 全线程、全协议 aborted 均为 0。

影响　v3（只锁行）在这一轮不会产生幻读，v4/v5 防住的幻读本来就不存在；三者的差别只剩锁数量。项目的核心命题仍然悬空。

C无锁基线自己也随线程下降 3~6 倍，索引层是独立瓶颈

`include/index/btree.h`、`src/index/v2_btree_latch.cpp`

证据　`none` 从 t1 到 t32：YCSB-A 243k→42.8k、YCSB-E 176k→68.3k、TPC-C payment 551k→176k。没有任何事务锁参与也恶化到这一步，指向 `BTreeLatch` 的 `root_guard_` / `writer_guard_`。

影响　在任何并发结论成立之前，这一层要先解决；否则所有曲线都是两个瓶颈叠加的形状。

D事务工作 90~99% 被丢弃，且 attempted 吞吐本身也在下降

`src/txn/workload.cpp` 的四个 `run_*` 协议；no-wait 语义

证据　YCSB-A t32：record-2pl attempted 35,388 / committed 3,740；hierarchical attempted 40,498 / committed 421。attempted 从 t2 的 129k 掉到 t32 的 35k。

影响　这不是「重试太多」，而是每个事务都变慢、持锁时间变长、冲突窗口变大。需要先拆掉锁表的全局串行点，再谈 no-wait 的代价。

ETPC-C payment 与 new-order 不可横比

`src/txn/workload.cpp` 的 `payment()` / `new_order()`

证据　payment 只生成 3 个 update，`operations_per_transaction` 对它完全无效；new-order 才有 `tpcc_items_per_order` 循环。实测 t1 吞吐 551k vs 224k，差 2.5 倍。

影响　同一张图里并列会被读成「payment 更轻」。要么让 payment 也遵守 ops 参数，要么在报告里明确标注两者事务成本不同构。

F锁表容量上限被误当成冲突（跨主机）

`include/lock/remote_lock_manager.h` 的 `kRemoteLockSlotsPerShard = 64`

证据　单线程单客户端、`lock_conflicts` 恒为 0 的前提下，中止率仍随「每事务持锁数」单调上升：range 1/4/16/32 → 20/48/159/258 把锁 → 0/0/7/51 次中止。

影响　跨主机那 432 个 case 一个都没跑。要么把槽数提到 512，要么把 capacity 与 conflict 分开计数。

G矩阵脚本本身的三个缺陷

`scripts/run_formal_matrix.sh`

证据　① CSV 校验比对表头前缀，第一个 case 即中止（已修，未提交）；② `run_case` 失败即 `return 1`，配合 `set -e` 会让单个 case 超时终止整轮；③ `experiments/configs/*.json` 未被 runner 读取，配置与命令是两套东西。

影响　②和③仍在。单点超时丢整轮的代价在这一轮已经接近发生（r=128 t8 单例 118 秒）。
