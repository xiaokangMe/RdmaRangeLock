摘要

范围查询的并发控制只有一句话的难点：要保证的不只是"这一行别被同时改"，而是"这一段区间里不会凭空出现新行"。新行在事务开始时不存大，没有对象可锁——这就是幻读，也是范围锁全部复杂性的来源。

把 1976 年以来的方案摊开看，它们的差别并不在"谁更新、谁更先进"，而在一个判据上：锁对象的边界是由数据决定的，还是由查询决定的。按这一条判据，十五个命名方案收敛成四类，其余全是配套细节。

四句话概括：

第一，四类不是四个时代，是四个取值。record-2PL、System R、ARIES/IM 都在 A 类；next-key、prior-key、gap-lock 都在 B 类，只是"洞归谁"不同；Lomet 的多粒度 key range、SQL Server 的 RangeS-S、桶锁、精确区间锁、Citron 全在 C 类；谓词锁与 precision locking 在 D 类。所谓"新协议"，多数是同一类的另一个取值。

第二，B 与 C 的差别只有一个词：边界来源。B 的边界是现存键，所以冲突判定退化成"键相等"，一次哈希就够；C 的边界是任意值，必须维护区间索引做相交判定。桶锁之所以快，正是因为它把 C 的任意边界量化到对齐格子上，硬生生把"相交"变成了"相等"。

第三，我们缺的不是第六个协议，是三个工程细节。独立的插入意向模式、删除路径的洞保护、以及精确区间锁。前两个是几天的活，第三个已经落地（1022bc6），而它恰好是唯一能回答"桶宽是必要妥协还是设计缺陷"的对照点。

第四，Citron 是 C 类的极值点，也是唯一把这件事搬到单边 RDMA 上的公开工作。它用静态四叉线段树把任意区间分解成 O(log N) 个节点，最好情况 2 个 RTT。它没有开源。

本文的口径

只讨论单版本、纯封锁、B+ 树。MVCC、快照隔离、SSI、PostgreSQL 的 SIREAD 一律不计入——它们用版本和依赖追踪解决区间问题，不靠锁，混进来会让分类失去意义。

性能数字标明来源。锁数量取自本项目 10 000 键正式矩阵（commit 8511d5b，YCSB-E，单线程），只用于说明协议之间的数量关系，不代表当前实现的绝对吞吐——本地授权后端已在 11-06 换掉，同一格快了 21–153 倍，正在重测。

1问题的形状：谓词不是对象

范围查询在语义上是一个谓词 P（如 k BETWEEN 20 AND 30）。事务 T1 在 t1 读到满足 P 的集合 S1，T2 在中间插入一条也满足 P 的记录并提交，T1 在 t2 再读得到 S2 ⊋ S1——两次读到的东西不一样，这就是幻读。

锁要做的事是把"P 覆盖的范围"变成一个可枚举、可比较、可存放的对象集合。这条链上有三次映射，每一次都失真一次：

谓词 P（age BETWEEN 20 AND 30）
  │  ① 依赖索引结构：只有能由索引顺序判定的谓词才能落到区间上
  ▼
索引上的连续对象（若干 key + 若干空隙）
  │  ② 选择粒度：记录 / 间隙 / 半开区间 / 整段区间 / 子树
  ▼
锁集合（一事务 1 把 ... 1235 把）
  │  ③ 选择存放位置：本地哈希、本地有序表、远端静态数组
  ▼
锁表条目

第 ① 步失真的后果是"索引依赖"：换成哈希索引，或者查询带非索引谓词，next-key 这套机制直接失效，只能退化成全表锁。第 ② 步决定锁数量与冲突面——这是我们在实验里能测的那根轴。第 ③ 步决定每把锁的单价，在远程场景下它是 5 次单边往返。

还有一个不变式必须先立起来，否则后面所有讨论都没有判据：一个正确的范围锁集合，必须覆盖查询区间上所有"可能插入新键的位置"，而不只是已存在的行。record-2PL 违反它，因为插入点落在两条记录之间时没有对象可锁；next-key 满足它，因为 (prev, cur] 首尾相接、不留空隙；桶锁也满足它，只是用"整桶"这种更粗的覆盖，方向是保守的（只会多锁，不会漏）。

2分类学：一条判据分出四类

判据只有一个：锁对象的边界从哪里来。

类边界来源冲突判定锁表结构锁数量随扫描

B 和 C 都在"锁一段"，为什么必须分开？因为边界的来源决定了实现的一切：

  • B 的端点就是 B+ 树里真实存在的键。锁 (1174, 1180] 时，右端点是真实记录、左端点是它的前一条记录。锁表按 key 直接查，一次哈希判冲突，不必知道"这两条记录之间还有多少空间"。
  • C 的端点由查询指定。锁 [1000, 1008) 时，两个端点可能都不是现存键。没有键可查，只能维护"谁锁了哪些区间"的索引，用相交判断冲突。

这一个差别带出三个连锁后果，后面第 6 节展开：冲突判定的复杂度、锁能不能渐进地装、锁数量是否随扫描线性增长。

4逐类拆解

4.1　A 类：点锁——正确性的天花板是定义决定的

record-2PL（严格 2PL）：范围读对每一行加 S 点锁，点写加 X 点锁，写入挂进写集合，事务结束先应用写集合再一次性解锁。严格性不是可选项：写是延迟应用的，X 锁必须持有到落地之后，否则会读到脏数据、产生级联回滚。

它在 A 类里是"最正确"的实现，但幻读是定义上的失效，不是实现 bug：插入的行在事务开始时还不存在，没有对象可锁。任何"只锁已有对象"的方案都躲不开这一条。

System R 的 key lock 是这条线上最早的工程化答案：把锁挂在索引项上，并用 index-level lock 兜底（没有可用索引时退化成表级）。ARIES/IM 走了另一条路：不锁 key，只锁 record 并配合页 latch，把"结构一致性"和"逻辑隔离"彻底分开。这两者的对比说明一件事——锁对象的选择首先取决于"你能不能为谓词找到一个稳定的枚举单位"，键、记录、页都是候选，代价各不相同。

4.2　B 类：半开区间——三种切法，一个不变式

B 类的共同点是：区间端点一定是现存键。三种切法只是"洞归谁"不同：

表 4-1　B 类内部的三种切法
方案区间记录是否一起锁特点
next-key(prev, cur]，往左看锁（含右端点）一行一把，最精确
prior-key[cur, next)，往右看锁（含左端点）无需构造 +∞ 哨兵
gap-lock洞本身不锁记录（可另加）锁更少，边界更粗

next-key 为什么能防幻读：一次扫描从 s 到 e，装的是 point(s) 起点锁 + 每行的 (prev, cur] + 尾区间 (last, e]。这些区间首尾相接、不留空隙，任何落进 [s, e] 的新键都必然落进某一段 (prev, cur]，从而与已有锁冲突。这一句就是它的正确性证明，也是它锁数量的来源：扫 8 行要 10 把，扫 1 215 行要 1 235 把。

prior-key 是它的对偶，有一个实现上的便利：[cur, next) 的右端点如果越过末尾就是 +∞，而 next-key 需要显式造这个人造键来覆盖"最后一条记录之后"的空间。

三个配套细节，缺一个都会漏：

  • 插入意向模式（SQL Server 的 RangeI-N，InnoDB 的 insert intention）。插入要问的是"这个洞里有没有人在扫"，而不是"这个洞能不能读"。把它做成独立模式（与所有模式兼容，只在插入前做测试）可以避免用 S/X 硬扛带来的过度阻塞。Lomet 1993 把它形式化为 range insert 模式。
  • hole lock：删除事务已经删掉一行但还没提交时，那个位置由谁来挡？做法是删除也要拿 next-key 锁并持有到提交。
  • ghost record：另一种做法——不物理删除，只打标记，让洞变成一条实实在在的记录，从而始终被锁覆盖。

4.3　C 类：任意区间——精确与近似的分水岭

C 类的锁对象是查询给的区间 [lo, hi)，端点不必是现存键。它的收益是锁数量与扫描宽度脱钩，代价是必须维护区间索引、必须做相交判定。

精确派

  • Lomet 1993 的多粒度 key range locking：半开区间 + 独立 range insert 模式，把"锁什么"和"插入可行性测试"拆成两件事。
  • SQL Server 的 RangeS-S / RangeS-U / RangeX-X / RangeI-N：把区间当单一锁对象注册进锁表，键是 (index, lo, hi)，而不是每行一把。
  • 我们的 exact-range（1022bc6）：一个独立的 LockKind::ExactRange，一次范围查询发布一条 [lo, hi)，端点开闭由 KeyRangeEnt 精确表示，与 next-key 共用同一张锁表，可直接做锁数量与冲突的隔离实验。
  • Citron：把区间分解到静态四叉线段树上，用单边 RDMA 原子操作完成加解锁，第 8 节详述。
  • 文件系统的老本行：POSIX 字节范围锁（fcntl）、Lustre LDLM 的 extent lock（可以授予比请求更大的区间以减少请求次数）。它们和数据库的区间锁是同一个数学问题，只是键空间是字节偏移。

近似派

层级桶锁是 C 类的一个量化近似：把键空间按 key / b 切成定宽桶，锁对象是桶号，冲突判定从"区间相交"退化成"桶号相等"。这一步退化换来的是 O(1) 定位——桶号算出来就是数组下标，一次 CAS 挂上，这在远程场景下是决定性的优势。

代价是假冲突：桶里 256 个键在锁表中是同一个对象，A 读第 10 个键、B 改第 200 个键，明明不相干也要冲突。所以桶锁在宽扫描上锁数量少一个数量级，在点写上却把相邻键绑在一起互相踩。

一句话把 B / C / 近似三者的关系说清

next-key 用"现存键"切区间，精确区间锁用"查询值"切区间，桶锁用"对齐格子"切区间。三者解决的是同一个问题——一次扫描别拿上千把锁——区别只在切法精确到什么程度。桶锁不是另一个思路，它是 C 类的一个可行但失真的实现。

4.4　D 类：谓词——理论上正确，工程上不可直接判定

谓词锁是 1976 年那篇论文的原点：锁的不是数据，是条件本身。问题是"两个谓词是否可同时满足"是 NP 完全的，运行时无法判定，所以单版本系统里没有独立实现——所有工程方案都是在做"如何用键上的锁去近似谓词"。

precision locking 是个巧妙的折中：不预锁谓词，而是记录别人正在执行的谓词，读取时把返回的每一行拿去和这些谓词比对，命中就冲突。它绕开了可满足性判定，代价是只能事后发现、不能事前预防，因此从未进入主流产品。

GiST / R 树上的谓词附着（Kornacker 等）解决的是另一个前提问题：多维索引没有线性键序，next-key 的"前驱/后继"根本不成立，只能把谓词挂到树节点上并用 NSN（node sequence number）做版本校验。这条线说明：B 类的整套机制建立在"键空间全序"这个假设上，换索引形态，假设就没了。

5骨架与非锁机制

5.1　多粒度意向锁：它不定义锁对象，只定义如何组合

Gray 1976 的 IS/IX/SIX/S/X 不是"一种范围锁"，而是一个组合规则：任何事务在子节点加锁前，必须在所有祖先节点持有兼容的意向锁，顺序自顶向下。它把"我要读这一整棵子树"压缩成祖先节点上的一个 IS，从而让锁数量与"子树高度"而不是"叶子条数"相关。

我们的层级桶锁借用了这套模式（根 IS/IX、桶 S/X、记录兜底），但层级是键空间的三层（表 → 桶 → 记录），不是 B+ 树的树层。这两件事经常被混淆：桶的边界由 key / b 算出来，与树怎么分裂无关。

5.2　非锁机制：结构一致性与逻辑隔离是两件事

  • B-link 树（Lehman & Yao 1981）：不靠范围锁解决幻读，靠右指针 + 高键，扫描时沿着 next 走，分裂期间通过 link 跟上，因此不需要锁间隙。它回答的是"能不能不用范围锁"，比再多一个范围锁变体更有说服力。
  • ARIES/IM 的页 latch：每页一把读写锁 + crabbing（先持父页再拿子页，拿到就放父页）。latch 是微秒级、只保护"这次遍历时页结构不被撕坏"，不提供任何事务隔离，也不防幻读。它和事务锁是两个维度，名字里的 lock 容易误导。
  • B* 树锁定（Bayer & Schkolnick 1977）：自顶向下判断节点是否"安全"（不会分裂），安全就不必锁子树，是结构式的另一种解法。

三处偏差，都值得修

偏差一：gap-lock 是 B/C 混合，两头都不占。名义上它是 B 类（锁间隙），但实现是"一把 open(s, e) 整段 + 两个端点 + 每条记录"，边界取自扫描端点而非现存键，装锁方式按 C 类来，同时还顺带拿了一整套 A 类的记录锁。结果是：既付了 C 类的判定代价，又没拿到 C 类的锁数量优势——它在 range=8 上有 105 把锁，比 next-key 的 95.5 还多 10%。这大概是它在同负载上比 next-key 更慢的直接原因。

偏差二：桶锁把"相交"退化成了"相等"。这是它能 O(1) 定位的原因，也是它假冲突的来源。它属于 C 类，只是失真。这一点以前被我描述成"另一条思路"，不准确——它和精确区间锁是同一类里的两个精度。

偏差三：缺少独立的插入意向模式。gap-lock 用 S/X 硬扛插入测试，语义上能做到（不会漏），但会过度阻塞（不该挡的也挡）。SQL Server 用 RangeI-N、InnoDB 用 insert intention，都是把这件事拆成独立模式。

关于本表的吞吐：不作结论

同一批矩阵里 YCSB-E t=1 的吞吐是 record-2PL 32 403、gap-lock 26 195、next-key 40 666、桶锁 138 971 txn/s。这些数字来自 11-02 的旧授权后端（全局协调器 + 线性冲突扫描），锁多的协议被额外惩罚；11-06 换成本地原子状态槽后同格快了 21–153 倍，其中 next-key 的中止率从 58% 掉到 3.6%。所以这张表里的锁数量可用（它由协议决定），吞吐只能当"旧实现的相对关系"看。

8Citron 深读：静态线段树上的单边范围锁

Citron（Gao、Lu 等，清华，FAST'23，Citron: Distributed Range Lock Management with One-sided RDMA）是 C 类里唯一把问题搬到单边 RDMA 上的公开工作，也是我们最该对着做的那篇。

8.1　它要解决的瓶颈

已有的分布式范围锁管理器（DRLM，如 Lustre 的 interval tree）都靠服务端 CPU 中转：客户端发 RPC → 服务端 CPU 遍历动态结构 → 回包。两个代价：服务端 CPU 成为吞吐瓶颈；一次加锁要排 4–5 个 RTT 的队。Citron 的答案是让服务端 CPU 完全不参与，只用单边 RDMA 改对端内存里的静态结构。

8.2　三个数据结构选择，全是为了压 RTT

表 8-1　Citron 的三个设计选择
选择常规做法Citron理由
树的叉数二叉线段树四叉树高减半，每层一次 RDMA，RTT 直接减半
叶子粒度1 个单位64 个单位（一个 8 字节位图）一个原子操作覆盖 64 个单位
节点寻址指针按层序放进平坦数组，用下标算RDMA 不能用指针：Child(x,i)=4x-2+i，Parent(x)=⌊(x+2)/4⌋

N = 2²⁸ 时共 560 万个节点、占 42.7 MB——相当于 1 TB 空间按 4 KB 页切分的 0.004%。

8.3　节点格式：每个都是 8 字节，两类语义完全不同

叶子：64 位位图，每一位对应一个存储单位；置位 = 被占用。用 masked-CAS 置位/清位。

内部：六个字段塞进 64 位
  Exp 1b | Occ 1b | TCnt 15b | TMax 15b | DCnt 16b | DMax 16b
        └── 两组面包店算法（Lamport bakery）票号：Max 发号、Cnt 叫号
            TCnt 管本节点，DCnt 管后代

15 位的计数器把并发客户端限制在 32 767 以内。这一段是它最"不通用"的地方——字段布局是把并发控制算法硬编码进 8 字节，换一个字段宽度就要重排全部原子操作。

8.4　加锁协议：一步本地计算，四段网络动作

  1. 步 1（零网络流量）：把 [l, r) 拆成若干树节点。它既不锁"覆盖范围的最小节点"（那样 [N/2-1, N/2+1) 会锁住根，造成全库冲突），也不锁 Θ(log N) 个节点（那要串行做很多次 RDMA），而是把它归结成树上的背包问题：最多用 k 个节点覆盖区间，目标是多余覆盖最小。实现里固定 k = 2，求解 < 0.5 µs，纯本地计算。
  2. (a) 拿票：内部节点先用 masked-FAA 对 TMax 取号，再轮询 TCnt 等叫号。
  3. (b) 查祖先：反复读祖先，若有 Occ 就等它释放；读到 Exp（扩容）就放弃重来。
  4. (c) 占位：内部节点置 Occ；叶子用 masked-CAS 置位。CAS 连续失败太久则升级到父节点重来（避免饥饿）。
  5. (d) 通知祖先：每 m 级通知一次，并等 m 层内的后代。

8.5　两个关键技巧

MITM 通知（m = 4）。问题是小范围请求（在叶子上）和大范围请求（在祖先上）互相不知道对方。全上溯到根代价太大，让大范围检查所有后代又是指数爆炸。Citron 取中点：小范围只通知每 m 级祖先，大范围只检查 m 层内后代，这样双方区间必然相交。大范围每次读 5 个节点，且这些节点在平坦数组里连续，5 次读可以合并成 4 次。

用本地时钟证明"通知已完成"。大范围在检查后代前要等 T_wait，但它无法确定小范围是否已通知完。解法是小范围用本地时钟验证：

t2 − t1 ≤ (1 − δ) · T_wait        δ = 10⁻⁴

其中 t1 是它最后一次读到"对方已占用"的时间、t2 是通知完成时间。只依赖时钟频率稳定（±100 ppm），不要求时钟同步，也不需要全局时钟。这条是整个设计里最精巧的一处，也是最难正确实现的一处。

优化到 2 个 RTT：同 QP 内单边操作不乱序（RC 保证），(a)(b) 可乐观合并提交、(c)(d) 也可合并（失败回滚 DCnt）；若节点的子节点全是叶子，直接 CAS 置 256 位，成功就跳过 (d)。最好情况两次往返拿到锁。

一个必须先想清楚的实验设计问题：Citron 的价值来自 O(log N) 分解，而我们的键空间只有 2×10⁶。N = 2¹⁴ 时四叉树只有 4 层，一次扫 128 行可能只覆盖 1–2 个叶子（叶子管 64 个键）。在这种规模下它的锁数量是 1–2 把、桶锁是 12–16 把，差异已经不是论文里"5 次往返 vs 1 次"的量级。

所以定位要选清楚：把它当作"C 类的精确代表"，用来回答"桶宽是必要妥协还是设计缺陷"，而不是"Citron 比桶锁快多少倍"。这个定位下，M0–M1 + M3 就够，不需要为它重建整套存储。

10开放问题与下一步

这份调研最实际的产出，是下面这张清单——按"能不能用现有数据验证"排序，而不是按理论重要性。

能立刻做的（已有代码或只差一组实验）

  1. 精确区间锁 vs 桶锁：exact-range 已实现，测同一格（YCSB-E r=128、θ=0.5、32 线程）看两件事——锁数是否真的从 16 把降到 1–2 把，中止率是否从桶锁的水平回落到 next-key 附近。这一格就能回答"桶宽是必要妥协还是设计缺陷"。
  2. 把 gap-lock 清理成纯 B 或纯 C：现在是两头不占的混合体，range=8 上比 next-key 还多 10% 的锁。清理后它的定位才清楚。
  3. 补插入意向模式：让插入测试独立于 S/X，减少"该放行的被挡"这一类过度阻塞。

需要新代码的

  1. 删除路径的洞保护：现在 (last, e] 尾区间有处理，但"删除—回滚—重插"这条路径的语义没有专门验证。hole lock 或 ghost record 二选一。
  2. B-link 结构式方案：用右指针 + 高键替代范围锁，回答"能不能不用范围锁"。这比再加一个范围锁变体更有说服力。
  3. Citron 的 M0/M1：平坦数组 + 背包拆分 + 单机协议，先验证拆分策略在我们的键空间上是否划算，再决定要不要碰 RDMA。

已知但短期不做的

  • 多维索引（GiST/R 树）：B 类整套机制依赖键空间全序，换形态假设就没了，属于综述里的一节而不是实验。
  • 跨分片范围锁：范围跨节点时如何组合，是分布式的事务问题，不是锁对象问题。
  • MVCC / SSI：不在本文范围内；需要说明的是"快照隔离不是范围锁的替代品，而是把冲突推迟到提交时刻"，写偏斜依然存在。
